# Security contact information for MessageFoundry, per RFC 9116.
# https://www.rfc-editor.org/rfc/rfc9116
#
# This file says only WHERE to send a report. The policy itself -- what to
# include, the coordinated-disclosure ask, the remediation windows, and the
# authorization and safe-harbor terms for good-faith research -- is the Policy
# URI below, and is deliberately not restated here. Two copies of a commitment
# drift, and the drifting copy is the one a researcher reads.
#
# THIS IS A STATIC DISCLOSURE FILE, NOT ENDPOINT DISCOVERY. The engine performs
# no .well-known discovery of any kind. SMART endpoints are operator-pinned per
# docs/adr/0024-smart-backend-services-token-provider.md, and the OIDC relying
# party per ADR 0142 -- two subsystems, so two citations. A search for
# ".well-known" that lands here has found an unrelated thing.
#
# EXPIRES IS A COMMITMENT TO RE-CHECK, NOT A FORMALITY. Past the date below a
# reader should stop trusting this file (RFC 9116 section 2.5.5), so renewing it
# means confirming both Contact channels still reach a maintainer and only then
# raising the date. Bumping the date alone discards the field's whole value.
#
# NO Canonical FIELD IS PUBLISHED, DELIBERATELY. RFC 9116 section 2.5.2 says a
# file whose Canonical URI does not match the location it was retrieved from
# should not be trusted, so naming a URI that no host currently serves would
# instruct parsers to distrust this file. Add Canonical in the same change that
# starts serving this file over HTTPS, and not before.
#
# Contact fields are in decreasing order of preference, which is what RFC 9116
# section 2.5.3 means by their order. The email address is second and is the
# fallback that needs no account.
