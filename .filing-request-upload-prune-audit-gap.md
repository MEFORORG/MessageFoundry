# Filing request: stopping the upload retention runner mid-sweep deletes files with no `upload.prune` audit row

From Manager busy-elgamal-b1c6a6 (acct-1), batch 137. Found while diagnosing a flaky test that reddened engine PR 1576. Please allocate a vault number and file it. This file is untracked and will be deleted once filed.

**Proposed heading:** `UploadRetentionRunner.stop()` cancels a sweep while `asyncio.to_thread(_prune)` keeps deleting, so files removed in that window get no `upload.prune` audit row

**Cluster:** audit / uploads (verify against the ledger's Cluster vocabulary). **Priority:** P2 (proposed). **Verdict:** build.

**Severity:** conditional (CLAUDE.md section 0). Zero deployments. On a first deployment, an engine shutdown that lands during a retention sweep would delete uploaded files with no audit record of the deletion. That is an audit-completeness gap on files that can carry PHI.

## Evidence

- A Builder reproduced it deterministically with a throwaway test (not committed): hold the runner's first `_prune` scan until the app lifespan exits; the file is deleted and no `upload.prune` row exists.
- Mechanism (reading): `stop()` cancels the task awaiting `asyncio.to_thread(_prune)`; cancelling the await does not stop the worker thread, which finishes the deletes, and `_audit_upload_prune` never runs.
- It surfaced as the flaky `tests/test_upload_api.py::test_the_RUNNER_prune_audit_row_also_names_the_system` ("got []"), seen on a push to main (run 36224250983), PR 1573's merge group (36234397019), a dependabot PR (36227922058) and PR 1576 (36238303230). That test is being made deterministic separately (test-only); this item is the product gap underneath it.

## Suggested fix

Let the thread's deletions be audited even on cancel: have `stop()` await the in-flight sweep (bounded), or have `_prune` return what it deleted and audit in a shielded step, or audit per file inside the thread's result path.
