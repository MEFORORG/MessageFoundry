- **A DATABASE send whose rollback fails would now discard its connection.** In the shipped code,
  when the rollback after a cancelled send failed, or the send's own rollback after a failed
  statement did, the connection went back to its pool. On a session still alive the INSERT stayed
  open, and the next send's commit would have committed it with its own: a row the engine counts
  as not sent, which a retry would write again. The connection is now closed after its cursor,
  inside the call gate, and the pool gets it back closed and is woken for it, so a waiting
  borrower or pool close is not left asleep. The close does not guarantee the server drops the
  transaction: a disconnect after a failed rollback can leave the session, and its locks, open
  until the server ends it (ADR 0159). A send that failed with a driver error is classified as it
  would be had the rollback passed, and a rollback that failed with a transient state makes it
  transient, so a dropped link retries rather than reaching the internal-error arm, which
  dead-letters by default. A send that failed with no driver error still raises the rollback's
  error. (`BACKLOG #5010`)
