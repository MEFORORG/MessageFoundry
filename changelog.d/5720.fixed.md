- **A store open that fails or is cancelled no longer leaks what it built.** On PostgreSQL and SQL
  Server a cancel skipped the failed open's cleanup, which caught `Exception` only, so the pool
  stayed open, and on SQL Server the pool's executor threads stayed too, a cancel while the pool
  connected included. A cancel no longer cuts the cleanup short: it gets up to 5 seconds more to
  finish, then what the open built is released without waiting for it, and the cancel is still
  raised. A cancel the task had swallowed before the open no longer turns the open's own failure
  into a cancel. The server backends still forfeit, rather than settle, the AES-GCM invocation
  block a failed open reserved, which only over-counts the key's use. On SQLite a read connection
  whose first PRAGMA failed was not tracked, so its non-daemon worker thread outlived the failed
  open, and a cancel during the failed open's cleanup could skip closing the writer; its cleanup
  settles the reserved block only once the open has bound the cipher to the store's salt, and
  never before. The failed open's own cleanup log lines name a failure's class only.
