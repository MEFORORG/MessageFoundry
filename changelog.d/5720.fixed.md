- **A store open that fails or is cancelled closes everything it opened, and settles the AES-GCM
  invocation block it reserved.** On PostgreSQL and SQL Server the failed-open cleanup now also
  runs on a cancel, and goes through the store's own close, so the block reserved at open is
  settled rather than forfeited. No backend settles a cipher its open had not yet bound to the
  store's salt, since that cipher may count for another store or for none. On the server backends
  the settle at close is bounded at 60 seconds. On SQL Server a cancel while the pool dials
  releases its executor, and every teardown step in close runs even when the settle or an earlier
  step raises or is cancelled. On SQLite a read-pool connection is tracked before its first
  PRAGMA, and close keeps closing its connections when a cancel arrives, for up to 30 seconds
  after it. On all three backends a cancel that arrives while the failed-open cleanup runs waits
  for it, and the cleanup is cancelled once it has run 30 seconds; the open's own failure is
  logged by class and the cancel is raised. An open coroutine closed mid-way runs a synchronous
  teardown. These failure paths log at WARNING by exception class, with any traceback at DEBUG
  only. (`BACKLOG #5720`)
