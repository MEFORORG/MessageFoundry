- **A store open that fails or is cancelled now releases at least its pool, its SQL Server
  executor and its SQLite connections, a cancel included.** On PostgreSQL and SQL Server a cancel
  skipped the failed open's cleanup, which caught `Exception` only, so the pool stayed open, and on
  SQL Server the pool's executor threads stayed too, a cancel while the pool connected included. A
  cancel no longer cuts the cleanup short: it gets up to 5 seconds more to finish, then a forced
  release runs without waiting for it, and the cancel is still raised. On SQLite a read connection
  whose first PRAGMA failed was not tracked, so its non-daemon worker thread outlived the failed
  open, and a cancel during the failed open's cleanup could skip closing the writer. Some cases
  are still open, at least these: after a forced release on SQL Server the pool's free connections
  are not closed; and on SQLite a statement that ignores the interrupt keeps its worker thread
  running. On PostgreSQL and SQL Server a failed open still forfeits the AES-GCM invocation block
  it reserved, as before, and each forfeited block counts toward the key's fail-closed ceiling. On SQLite the cleanup settles the
  reserved block only once the open has bound the cipher to the store's salt, and never before.
  The log lines the failed-open cleanup adds name a failure's class only. (`BACKLOG #5720`)
- **More of a failed store open's cleanup holds against a cancel.** On PostgreSQL and SQL Server a
  failure while the store object is built no longer leaks the pool, and on SQL Server the executor.
  The one-connection store that `provision-schema` and `check-privileges` run on, and the close when
  `open_store` refuses to start a keyless audit chain, now run their close on an error the same way,
  so a cancel cannot cut it short; a close failure there is logged by class rather than replacing
  the error. On SQL Server, when the one-connection store's close fails before its pool step, the
  pool is closed and waited on for at most 5 seconds; past that it is left closing. A
  `GeneratorExit` thrown while the cleanup waits now runs the forced release and is re-raised. A
  cleanup that ends cancelled, whether or not the open still waited for it, is logged at WARNING
  rather than at ERROR where a forced release then ran; where there is none to run, as on the
  keyless-chain refusal's close, it is still logged at ERROR as possibly not released. A loop holds
  at most 64 unfinished abandoned cleanups. `MessageStore.close()` now logs a failing step by class
  at WARNING, its traceback at DEBUG only, and the PostgreSQL and SQL Server closes log a failed
  settle the same way. The `aiosqlite` floor is now 0.22.1, the first release with the
  `Connection.stop()` the SQLite forced release calls. (`BACKLOG #5720`)
