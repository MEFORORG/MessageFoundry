- **A store open that fails or is cancelled closes everything it opened, and settles the AES-GCM
  invocation block it reserved.** On PostgreSQL and SQL Server the failed-open cleanup now also
  runs on a cancel, and goes through the store's own close, so the block reserved at open is
  settled rather than forfeited. No backend settles a cipher its open had not yet bound to the
  store's salt, since that cipher may count for another store or for none. On the server backends
  the settle at close is bounded at 10 seconds, so a degraded server cannot hold the pool open. On
  SQL Server a cancel while the pool dials releases its executor, and every teardown step in close
  runs even when the settle or an earlier step raises or is cancelled. On SQLite a read-pool
  connection is tracked before its first PRAGMA, and close runs its connection teardown to
  completion through a cancel, so no worker thread is left running. On all three backends a cancel
  that arrives while the failed-open cleanup runs waits for it, up to 30 seconds, after which the
  cleanup is cancelled; the open's own failure is logged by class and the cancel is raised. An open
  coroutine closed mid-way runs a synchronous teardown. The cleanup and the settle log the failure
  class only, with no driver text. (`BACKLOG #5720`)
