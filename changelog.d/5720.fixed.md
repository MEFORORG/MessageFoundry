- **A store open that fails or is cancelled now releases at least its pool, its SQL Server
  executor and its SQLite connections, a cancel included.** On PostgreSQL and SQL Server a cancel
  skipped the failed open's cleanup, which caught `Exception` only, so the pool stayed open, and on
  SQL Server the pool's executor threads stayed too, a cancel while the pool connected included. A
  cancel no longer cuts the cleanup short: it gets up to 5 seconds more to finish, then a forced
  release runs without waiting for it, and the cancel is still raised. On SQLite a read connection
  whose first PRAGMA failed was not tracked, so its non-daemon worker thread outlived the failed
  open, and a cancel during the failed open's cleanup could skip closing the writer. Some cases
  are still open, at least these: after a forced release on SQL Server the pool's free connections
  are not closed; on SQLite a statement that ignores the interrupt keeps its worker thread running;
  and on PostgreSQL and SQL Server a failure while the store object is built, after the pool is
  created and before the cleanup's `try`, still leaks the pool. On PostgreSQL and SQL Server a
  failed open still forfeits the AES-GCM invocation block it reserved, as before, and each
  forfeited block counts toward the key's fail-closed ceiling. On SQLite the cleanup settles the
  reserved block only once the open has bound the cipher to the store's salt, and never before.
  The log lines the failed-open cleanup adds name a failure's class only; `MessageStore.close()`,
  which the SQLite cleanup runs, still logs its own failures in full, as before.
  (`BACKLOG #5720`)
