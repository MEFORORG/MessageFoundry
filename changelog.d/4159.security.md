- **A start now refuses a CRL that the CA it names by key identifier proves badly signed, even
  beside a CA of the same name that has no subject key identifier.** Before, that second CA could
  rescue the CRL: where its key verified the CRL, the start loaded the file with no warning, and
  where the engine could not check its key, the start loaded the file with a WARNING. Now such a
  CA counts for nothing once the CRL names another listed CA's key, and the running-hop reload
  holds such a file back too. A CA the CRL names that cannot be checked still warns, and so does a
  lone CA with no subject key identifier that cannot be checked. A signature the CA's key accepts
  is now verified even where the `cryptography` library's own check refuses it, as for an RSA
  signature over SHA-1 the CA made, so the verdict no longer depends on the digest: a start loads
  such a CRL with no warning, and the reload applies it where it held it back before. The premise,
  that the engine's verifying contexts use strict verification, and the cases where the start can
  refuse a CRL a handshake could pass are stated in `docs/CONFIGURATION.md`, in the paragraph
  that starts "Why a CA with no subject key identifier counts for nothing there". (vault BACKLOG
