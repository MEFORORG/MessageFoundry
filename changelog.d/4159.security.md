- **A start now refuses a CRL that the CA it names by key identifier proves badly signed, even
  beside a CA of the same name that has no subject key identifier and cannot be checked.** Before,
  that second CA made the signature check read "cannot check", so the start loaded the file with a
  WARNING. The verifying contexts the engine builds use strict verification, and OpenSSL 3
  refuses a chain of two or more certificates through a CA with no subject key identifier. A CA
  the CRL names that cannot be checked still warns, and so does a lone CA with no subject key
  identifier that cannot be checked. The running-hop reload still holds such a file back. The
  start can refuse a CRL a handshake could pass in at least two cases: a peer that presents such a
  CA alone, as a one-certificate chain, which OpenSSL does not check strictly, and an OpenSSL
  build without that strict check; the engine sets no OpenSSL version floor. (vault BACKLOG
