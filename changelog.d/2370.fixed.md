- **An unreadable CA file is the named refusal on the `tls_verify=false` arms too.** The SMTP
  context (Email, Direct and the alerts sink), the MLLP destination and the FTPS context loaded
  the CA file themselves when `tls_verify=false`, so a missing file was a bare
  `FileNotFoundError`, and one with no usable PEM a raw `ssl.SSLError`, naming nothing. They now
  raise `CaFileUnreadable`, naming the setting and, where there is one, the connection, and not
  the path, as the verifying arms already did. The same holds for an MLLP, DICOM C-STORE SCU or
  FTPS context built directly with no `[tls]` policy, which the engine itself never does. Such a
  hop still refuses a CA file it cannot read, and a CA file that loads is trusted as before.
  (`BACKLOG #2370`)
