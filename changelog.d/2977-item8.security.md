- **A REST destination with `ech_egress` and `verify_tls = false` is now judged by the revocation
  guard.** With an ECH sidecar the sidecar makes the TLS connection to the peer, so `verify_tls`
  reaches no TLS connection the engine makes and turns off no verification. It did turn off the
  revocation guard: an off-loopback hop on an enforcing instance built with no revocation
  attestation, while the same hop with `verify_tls` on was refused unless `tls_revocation_attested`
  was set with its reason. That hop now needs `tls_revocation_attested` too, as well as the
  `tls_hop_attested` its `verify_tls = false` already needed, and its refusal names that
  attestation. A direct `verify_tls = false` hop, with no sidecar, is unchanged. (`BACKLOG #2977`)
