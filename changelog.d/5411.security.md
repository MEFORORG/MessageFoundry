- **The IDE Security Settings editor now checks a user-set `messagefoundry.serviceConfig` that
  reaches the workspace folder by another spelling, and a `.code-workspace` file can no longer
  choose the folder a path is checked against.** A user-set path outside the workspace folder is
  no longer always accepted as written. On Windows it is refused before any read when a folder or
  file name on it ends in a dot or a space, holds a colon or is a device name, and otherwise has
  each folder on it read, by real path and by device and file id. Where it reaches the workspace
  folder through a junction or a directory symbolic link outside the folder (by real path) or a
  UNC loopback admin share (by file id), the three spellings measured on Windows with standalone
  Node v24.20.0, not the editor's Electron runtime, the part below the workspace folder gets the
  same checks as a path inside it. Such a path is refused when a folder on it cannot be read or is
  a dangling link; a path that reaches no folder inside is accepted as written. In a window opened
  from a `.code-workspace` file, which chooses the workspace folder, a path inside that folder is
  refused, the default `messagefoundry.toml` included, unless the folder lies inside the folder
  holding the file, and a user-set path in the file's own folder, or placed in it by the same
  reads, gets the link checks from there. Open limits include at least: other spellings, a subst
  drive among them, are unmeasured and may be accepted as written; where the workspace folder
  reports no file id, a UNC alias of it is accepted as written, no looser than before; an alias
  whose target passes through a link the repository holds, at any depth (an alias onto
  `ws\linked\deeper`, measured), is followed where that link leads, unchecked; in a
  `.code-workspace` window, a relative user value that leaves the workspace folder by `..` is read
  against the folder the file chose, and is accepted as written when it reaches no folder inside;
  and a link made or a folder renamed between the check and the CLI's write is not seen. The rules
  and the open limits are in the `securityConfigTarget` docblock in
  `ide/src/securityEditorModel.ts`. (`BACKLOG #5411`, `BACKLOG #8237` items 16 and 57)
