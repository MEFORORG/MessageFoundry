- **A credential in a proxy URL no longer reaches a second proxy in cleartext.** With `http` and
  `https` mapped to different web proxies, the urllib egress would have sent the first proxy's
  credential to the second one in a cleartext `CONNECT`. urllib keeps the header when it hands a
  request on, and the check read only the current proxy's URL. It now reads the header too, at
  every proxy. A credentialed proxy written `https://` is now refused for an `https` target as
  well, because urllib sends `CONNECT` with the header before any TLS. A connection's `proxy_url`
  serves both schemes, so the engine now refuses every send to an `https` target through a
  credentialed `proxy_url`. It refuses a send to an `http` target too. The one measured exception
  is a proxy written `https://` whose own host urllib's bypass list matches. Those sends go to the
  proxy over TLS, and nothing in this check verifies that TLS. The Vault hop picks one proxy per
  request and did not leak. What the check still does not cover is listed in [CONNECTIONS.md](../docs/CONNECTIONS.md). (`BACKLOG #3410`)
