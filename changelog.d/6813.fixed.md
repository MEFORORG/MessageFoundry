- **The sandbox worker lets go of the failed request and its frames before it builds an
  out-of-memory reply, and a torn reply frame is not followed by another.** A worker that ran out
  of memory built its `memory` reply while still holding the raw request frame and the decoded
  request, and with garbage only a cycle still held uncollected, so the reply could fail for want
  of memory and the parent read a crash instead. It now clears the error's traceback and chain,
  drops the frame and the request, and collects cycles first. That cannot free all the call
  left held, at least not a global, a cache or a thread, so the reply can still fail there. A reply
  write that failed with `OSError` was followed by a second, error frame, which could land after a
  partly written one; the worker now logs the failure and exits without writing another. The
  parent then fails the message, or reads the frame whole where the flush at the worker's exit
  completes it, and starts a fresh worker for the next. (`BACKLOG #6813`)
