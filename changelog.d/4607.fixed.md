- **A worker killed mid-handoff by an error that is not an `Exception` no longer strands its row.**
  The stage workers catch `Exception` only, so such an error killed the task with its claimed row
  in flight. Before, a per-lane worker's replacement then claimed past that row and delivered its
  successors first, and in the pooled claim mode a lane serializer killed that way was not replaced
  at all, so its lane stopped draining. Both lasted until the next start. Now the replacement
  re-pends the rows the dead task held before its lane claims again, with the same hold-and-retry,
  leadership gate and pause and halt ends as a failed re-pend after a store fault, so per-lane order
  holds with no restart. The re-pend counts as a retry, so a replacement on a node that is not the
  leader holds its lane and waits, as a held retry does, and sends none once the node leads under
  another lease, since a successor may hold the rows. In the pooled claim mode the serializer is
  respawned for this, a batching outbound's coalesced rows are re-pended with its head, and the
  replacement returns its processing slot while it waits. A row that kills its worker every time
  now holds its lane. In the per-lane claim mode the respawn backs off after a repeat death, the
  death is logged on a backoff (the 1st, 2nd, 4th ...), `lane_stuck` is paged once the deaths reach
  `infra_fault_stop_after` with no pass settling between them, and the row is never dead-lettered,
  as a row whose handoff faults every pass is not. A death five minutes or more after the last one
  starts a new run, so rare unrelated deaths on an idle lane do not page. In the pooled claim mode
  a death on the first row of the serializer's batch counts as a zero-progress infrastructure
  fault, so `infra_fault_policy` STOPs the lane or pages `lane_stuck` as for any persistent fault;
  a death past the first row counts as progress. The serializer deaths are also counted, and a run
  of `infra_fault_stop_after` of them with no serializer finishing its batch between pages
  `lane_stuck` once, unless that recovery's own fault reaches the bound and alerts instead. The
  replacement reads the store's in-flight rows to tell whether the dead task wrote a row it held,
  and if it did the death counts as progress and ends the run of deaths. A death with none of the
  rows the dead task held in flight counts. Where the batch is handed off strictly in order one
  row at a time, so does one with fewer in flight than it held: a per-lane router or transform
  batch, where the row written may be one before the row it died on, as a pooled death past the
  first row of its prefix counts as progress, and a pooled prefix of 2 or more with no coalesced
  rows beside it, counted from the row it died on. So a lane that writes a row at every death is
  neither STOPped nor paged as stuck when it holds one row at a time or a batch of those kinds. A
  per-lane delivery batch, which is an unordered lane's claim or a batching outbound's coalesced
  rows, and a pooled prefix with coalesced rows beside it, count only a death with none of their
  rows in flight, so such a lane that writes some of its rows and then dies every time still reads
  as stuck: it backs off and pages `lane_stuck`, and a pooled one STOPs under `stop`. On an
  unordered per-lane lane a pass that settles closes a run of deaths only once it has resolved
  every row that all of the run's deaths held, so a poison row that fresh rows pass still reaches
  the backoff and the page; a row the dead worker wrote before it died can keep such a run open
  until the five-minute gap, so a death inside it counts as a repeat. A pooled
  replacement that owes no write no longer holds its lane while this node is not the leader, and
  a stop that ends it is not counted against the demotion drain. The logged `lane_stuck` line no longer
  says `retry_forever`, since a run of deaths pages it under either policy. A stop
  of the engine leaves the rows for the next start, and a cancelled task leaves them with no log
  line. Where a stop ends a pooled recovery before its re-pend lands, the dispatcher's drain on a
  demotion no longer reports zero rows in flight. (`BACKLOG #4607`)
