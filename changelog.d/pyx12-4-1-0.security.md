- **The `[x12]` extra now needs pyx12 4.1.0, upstream's security release.** Under pyx12 4.0.1 a
  997/999 ack copied sender values as they came, so a hostile value holding the ack's own
  separators could forge ack structure, and pyx12's error records carried the offending data value.
  4.1.0 writes `?` for the ack separators, control characters and non-ASCII in most values it
  echoes, and cuts an echoed bad value at 99 characters, so an ack can now differ from the sender's
  text there, sender and receiver IDs included. Its error-handler records carry no data value unless
  `log_data_values` is on, which the engine does not set and a pyx12 config file can.
  4.1.0 does not close either class. At least these remain: a 997 copies the sender's ISA11 as-is;
  a 997 splits an `*` in an echoed GS06 into extra AK1 elements, and both writers split one in an
  echoed segment ID; and other pyx12 records can still carry input text, such as the exception it
  logs when its ack writer fails. The engine's own guards are narrower than that: it reads the ack
  type from pyx12's report rather than the ack text, returns no ack whose last write was not its
  IEA, and mutes the `pyx12` logger tree, which stays the control on what pyx12 logs. Hostile input
  whose element value holds one of the ack writer's delimiters ends as a returned validation result,
  not an uncaught error.
- **Long X12 segments read differently.** Under pyx12 4.0.1 a segment longer than about 8 KB
  silently ended the file, and only what came before it was validated. 4.1.0 reads it whole, and
  `validate()` raises `X12ValidationError` for a segment with no terminator within 1 MiB, so such
  input gets no result and no ack.
