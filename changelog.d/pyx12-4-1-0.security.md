- **The `[x12]` extra now needs pyx12 4.1.0, upstream's security release.** Under pyx12 4.0.1 a
  997/999 ack copied sender values as they came, so a hostile value holding the ack's own
  separators could forge ack structure, and pyx12's log records carried the offending data value.
  4.1.0 writes `?` for the ack separators, control characters and non-ASCII in most values it
  echoes, so an ack can now differ from the sender's text there, sender and receiver IDs included.
  Its log records carry no data value unless `log_data_values` is on, which the engine does not set.
  4.1.0 does not close the forgery class. At least these remain: a 997 copies the sender's ISA11
  as-is, and both writers still split an `*` in some echoed values, such as a GS06 or a segment ID,
  into extra elements. The engine's own guards are narrower than that: it reads the ack type from
  pyx12's report rather than the ack text, returns no ack whose last write was not its IEA, and mutes
  the `pyx12` logger tree. Hostile input whose element value holds one of the ack writer's
  delimiters ends as a returned validation result, not an uncaught error.
- **`validate()` raises `X12ValidationError` for a segment with no terminator within 1 MiB.** pyx12
  4.1.0 raises there, where 4.0.1 stopped reading and validated what came before. So such input, for
  example one very large segment, now gets no result and no ack.
