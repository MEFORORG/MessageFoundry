- **The `[x12]` extra now needs pyx12 4.1.0, upstream's security release.** Under pyx12 4.0.1 a
  997/999 ack copied the ack's own separators as they came in the sender values it echoed, so a
  hostile value holding them could forge ack structure, and pyx12's error records carried the
  offending data value. 4.1.0 replaces the ack separators, control characters and non-ASCII in
  most values it echoes, and shortens a long echoed bad value, so an ack can differ from the
  sender's text in more places, an echoed sender ID included. Its error-handler records carry no
  data value unless `log_data_values` is on, which the engine does not set and a pyx12 config file
  can.
  4.1.0 does not close either class. At least these remain: a 997 copies the sender's ISA11 as-is;
  a 997 splits an `*` in an echoed GS06 into extra AK1 elements, and both writers split one in an
  echoed segment ID; and an error pyx12 raises can quote input. For example, its `Map not found`
  error for an unknown GS01 or GS08 quotes both, and the engine's `X12ValidationError` chains that
  error as its cause, so a traceback of that exception carries those values. The engine's own
  guards are narrower than that. Among them, it reads the ack type from pyx12's report rather than
  the ack text, returns no ack whose last write was not its IEA, and mutes the `pyx12` logger
  tree, which stays the control on what pyx12 logs. A bad element value that holds one of the ack writer's
  delimiters, and that the ack echoes, ends as a returned validation result, not an uncaught error.
- **Long X12 segments read differently.** pyx12 4.0.1 could stop reading at a segment longer than
  about 8K characters. `validate()` then returned `valid=False` with interchange error `023` among
  its errors, and that segment and everything after it went unvalidated. 4.1.0 reads much longer
  segments, but `validate()` can raise `X12ValidationError` for a segment of about a million
  characters or longer, and then returns no result and no ack.
