- **A reload that runs while a log-write halt waits for the reload lock no longer rebinds a listener
  the halt then leaves bound over internal stages it shut down.** The halt marked its inbounds'
  internal stages only once it held the reload lock, and the rebind gate refused only an inbound
  already marked, so a reload holding the lock rebound every listener and the halt, which read its
  bound list before the lock, left them bound. The halt now marks every registry inbound's internal
  stages as it latches, before it waits; this pauses their pooled router, transform and response lanes, or
  wakes their per-lane workers to stop at their loop-top gate, the item already in flight still
  completing, and it makes the rebind gate refuse those inbounds. While the latch is set, the gate also
  probes the log before it binds an inbound that is not marked yet, and refuses and marks it if the
  probe fails. Once it holds the lock, the halt reads the latch and its lanes again: if a reload or
  start probed the log and cleared the latch meanwhile, it still stops, sets the latch again, and
  sends a second page under the sink label with `:latch-cleared` appended; it stops only the
  inbounds still bound and the owned outbounds not already paused, so it does not turn an outbound
  a reload engine-parked into an operator pause, and a second halt of the same break sends its own
  page but stops nothing and sends no further per-connection stop alert. A halt that finds the
  runner fully stopped when it gets the lock pauses nothing. A raise from the alert sink on the
  first page, or from the early stage marking, is logged and no longer aborts the halt; the first
  page's count comes from the lanes read before the wait. (`BACKLOG #5704`)
