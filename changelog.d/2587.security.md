- **A child process of the engine no longer inherits the engine's whole environment.** The engine's
  environment holds its secrets: the store key when it is supplied that way, the store password and
  every `MEFOR_VALUE_*` connection secret. The sandbox worker under `[sandbox].mode = "subprocess"`
  was started with a copy of all of it, so a Router or Handler there would have read them from its
  own environment. The worker now starts with a short allowlist: what the platform and the
  interpreter need, the `PYTHON*` variables, and `MEFOR_ALLOW_INSECURE_CONFIG_SOURCE`. The
  `[dr]` takeover and release hooks keep ordinary variables and lose every `MEFOR_*` variable and
  `VAULT_TOKEN`. An engine shard under `supervise` is a whole engine and still gets everything. The
  worker and the shards also start with `-P`, so the engine's working directory is not on their
  import path. **This is not an isolation boundary by itself:** a child still runs as the engine's
  account and can read what that account can read. Two things change for a config author. A Router
  or Handler that reads a variable from `os.environ` under `mode = "subprocess"` now finds it unset
  unless it is on the allowlist; use `env()`. A hook that read a `MEFOR_*` variable must be given
  the value another way. See `[sandbox]` and `[dr]` in
  [CONFIGURATION.md](../docs/CONFIGURATION.md) and the 2026-10-01 correction in
  [ADR 0087](../docs/adr/0087-sandbox-subprocess-isolation.md). (`BACKLOG #2587`)
