- **A SOAP fault's Sender or Receiver class is read only from its code element.** The code is now
  the Fault's first child, a comment, CDATA section or processing instruction before it stepped
  over whole: SOAP 1.1's `faultcode`, or SOAP 1.2's `Code` and the `Value` that is the Code's own
  first child. The shipped code took the Fault's first `Value` ahead of any `faultcode`, so a
  `Value` in a Subcode, Role, Node, Reason or Detail that came before the Code's own Value, or one
  ahead of a SOAP 1.1 `faultcode`, decided the class instead; on a first deployment that could have
  made a Sender fault read as a Receiver one and retry until the attempt limit. A Fault whose first
  child is neither, including a SOAP 1.1 Fault whose `faultcode` is not first, now reads as a
  permanent fault, as one with no code always did; it is never read as delivered. Unchanged: where
  a Fault is found, whether one counts, and the WS-Security check, which still searches the reply
  from where the Fault search starts, so a WS-Security code in any Fault text still dead-letters it.
  Only the first-child search steps over comments, CDATA sections and processing instructions; the
  Fault search and the Fault and Code close-tag searches still do not. So at least these replies
  with a real Receiver or Server fault, which the shipped code retried, now read as a permanent
  fault and dead-letter: a Fault start tag inside such markup in the Body ahead of the real Fault,
  since that tag is still the Fault found and its first child is then the real Fault's start tag;
  a `</Code>` inside such markup in the Code ahead of its Value; and a `<!` that opens neither a
  comment nor CDATA, such as a DOCTYPE, ahead of the code element. A whole Fault inside a comment
  ahead of the real one still decides the class with its own code, as it did in the shipped code.
