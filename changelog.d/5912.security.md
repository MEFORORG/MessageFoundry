- **A SOAP fault's Sender or Receiver class is read first from its code element.** The code is now
  read first from the Fault's first child, a comment, CDATA section or processing instruction before it stepped
  over whole: SOAP 1.1's `faultcode`, or SOAP 1.2's `Code` and the `Value` that is the Code's own
  first child. The shipped code took the Fault's first `Value` ahead of any `faultcode`. Where the
  first-child read yields a code, a `Value` inside a comment, CDATA section or processing
  instruction ahead of it no longer decides the class; on a first deployment that could have made a
  Sender fault read as a Receiver one and retry until the attempt limit. Where that first-child
  read yields no code, the code falls back to the shipped search, the Fault's first `faultcode` or a
  `Value` ahead of it, so a `Value` in a Subcode, Role, Node, Reason or Detail ahead of the code
  element, or one ahead of a SOAP 1.1 `faultcode`, still decides the class there, as in the shipped
  code. The fallback reads from the Fault start tag to its close tag outside markup, where the
  shipped search stopped at the first `</Fault>` anywhere. At least these shapes read as they did
  in the shipped code, and a Receiver or Server fault in them is still retried: a SOAP 1.1 `faultstring` before the `faultcode`, a SOAP
  1.2 `Reason` before the `Code`, a DOCTYPE or other `<!` that opens neither a comment nor CDATA
  ahead of the code element, a lowercase `<![cdata[`, and an unterminated comment inside the Fault.
  A Fault where neither read finds a code reads as a permanent fault, as one with no code always
  did; it is never read as delivered. Unchanged: whether
  a Fault counts, and the WS-Security check, which still searches the reply
  from where the Fault search starts, so a WS-Security code in any Fault text still dead-letters it.
  The Fault search, and the Fault and Code close-tag searches, step over terminated comments, CDATA
  sections and processing instructions too, so a Fault start tag, or a `</Fault>` or `</Code>`,
  inside such markup no longer decides the class; the Fault search reads the reply from its start,
  so this holds even where the Body start tag sits in that markup. Where every Fault start tag after
  the Body start tag is inside such markup, the first of them is still read as the Fault, as in the
  shipped code; with none after it, the first before it outside such markup is read, else the
  first before it. So such a reply never newly reads as delivered.
  Unchanged: a `</` inside a comment within the `faultcode` or `Value` itself still ends the code
  text, as in the shipped code.
