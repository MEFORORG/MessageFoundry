- **Four more verifying outbound hops are refused when they check no certificate revocation.** An
  https `FhirLookup` read, a `DICOM()` outbound with `tls = true`, an FTPS upload, and a `Direct()`
  outbound that sets a `username` each verified the peer certificate and ran no revocation guard.
  On a first deployment under the default `enforcement = enforce`, each would have accepted a
  revoked certificate with no refusal, warning or audit record. Each now takes the same
  construction-time refusal MLLP, REST and EMAIL take, at `messagefoundry check`, dry-run, reload
  and the serve pre-flight, when the peer is off-loopback. **A config that builds one of these hops
  to an off-box host is now refused** until one of these holds: `[tls].crl_file` reaches the hop, or
  the connection declares `tls_revocation_attested = true` with a
  `tls_revocation_attested_reason`. On a `FhirLookup` that one declaration covers both the read and
  its SMART token endpoint. A `Direct()` outbound with no SMTP credential is unchanged: its body is
  S/MIME-protected and it sends no login. **Not covered:** the inbound FTPS poll, the alert SMTP and
  webhook sinks, the AI broker and the LDAPS bind still run no revocation guard. See
  [DEPLOYMENT.md](../docs/DEPLOYMENT.md), *Revocation-guard behavior*.
