- **A DR activation reloads the directory the running graph came from.** `POST /dr/activate`
  reloads the graph under the DR run-profile. It used to reload the startup `--config` dir. On a
  first DR deployment, an activation after an operator reload from another allowed root would have
  put the older graph back, and nothing would have said so. It now reloads the directory of the
  last applied reload, else the startup dir, the same one `GET /config/provenance` checks. The
  cluster convergence reload still reads each node's own startup dir. (vault BACKLOG #2840)
- **The DR seed marker's config digest comes from the shared fingerprint rule, at activation.**
  The coordinator behind `POST /dr/activate` and `/dr/release` used to take that digest when it was
  first built, on the event loop, and it caught only `OSError`. A config file name that cannot be
  encoded as UTF-8 would have made every activate or release fail, for as long as that file stayed
  in the config dir. The digest is now taken off the event loop, when an activation writes its
  `dr_seed` row. It covers the directory that activation reloads, unless a reload from another
  root lands in between. The marker would then hold the earlier directory's digest: it is written
  before the takeover hook, and the reload runs after. Where the shared rule takes no digest, the
  marker records none and the activation goes on. (vault BACKLOG #2839)
- **A DR activation is refused before the takeover hook when its config directory cannot be
  listed.** `POST /dr/activate` now lists the directory it will reload before it recovers the
  store and before it runs the takeover hook. If the listing fails, the activation aborts as a
  `profile` refusal, so the hook would not run and the service address (the VIP) would not move.
  This is a new refusal. Where the last applied reload came from a directory that was later
  removed, an activation would be refused here. Before, it would have gone ahead on the startup
  directory's graph. To recover, reload from a directory that exists, or restart the service,
  then activate. (vault BACKLOG #2840)
