- **An outbound `tls_ca_file` is now checked at start and at every reload.** It gets the checks an
  inbound listener's CA already had. Every factory that takes `tls_ca_file` for an outbound hop now
  also takes an optional `tls_ca_pin`, the file's SHA-256. A pin that does not match refuses the
  start or reload, naming `outbound connection '<name>' tls_ca_file`. Under
  `[security].enforcement = enforce`, a file another account could replace, or one whose
  permissions the engine cannot read, refuses too. A changed file writes an `auth.trust_anchor`
  audit row under `outbound:<name>`, or `fhir_lookup:<name>` for a `FhirLookup()`. Before this,
  whoever could replace the file would have chosen which CA the hop trusts, with no record of it.
  One gap remains: the hop still reads the file again by path after the check, so a matching pin
  is no escape for a file whose permissions cannot be read. An outbound `MLLP()` or `DICOM()` with
  `tls = true` and a `tls_ca_file` now accepts `tls_ca_pin` instead of refusing it. At start, a
  file that cannot be read now refuses the whole start, as an inbound CA's does, rather than
  failing only its own connection.
  [CONNECTIONS.md](../docs/CONNECTIONS.md#the-engine-checks-the-file-at-every-start-and-reload-tls_ca_pin)
  has the details. (`BACKLOG #2371`)
