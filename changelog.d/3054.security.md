- **`audit-verify` exits 4, not 0, when a keyless chain walks clean in a shell whose settings
  require a store key.** The settings say verification is keyed, and a plain SHA-256 walk is not
  that, so the chain was not checked to their standard. A job that reads only the exit code never
  saw the `WARNING` it printed with exit 0. It now prints a `NOT CHECKED` line, keeps the `WARNING`
  on stderr, and exits 4. In that setup 4 is now the steady state, so a rewritten first row no
  longer moves a job off a passing code. Give the job the engine's key, or the keyless opt-out the
  engine runs under, to get a pass. A 4 from a job that exited 0 before means the job lost its key
  or its opt-out; nothing in the database can cause that move. See
  [SECURITY.md](../docs/SECURITY.md) "Tamper-evidence".
- A log that is empty in that setup no longer gets a warning saying its first row names no key,
  since it has no first row. It gets the empty-log warning and exit alone. The open refuses that
  state with exit 2 first, so the verify sees it only for a log emptied while the verify runs.
- `audit-verify` loads its settings as `audit-anchor` does, so a settings error is rendered by
  field and message and never stringified with the value it refused. Vault BACKLOG #3054.
