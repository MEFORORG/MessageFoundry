- **`audit-verify` exits 5, not 0, when a keyless chain walks clean in a shell whose settings
  require a store key.** The settings say the check is keyed, and a plain SHA-256 walk is not that.
  It prints a `NOT CHECKED` line and a `WARNING` on stderr naming the mismatch. In that setup 5 is
  the steady state, and a matching `--expected-anchor` does not change it. Exit 4 keeps its meaning:
  the first row names a key this shell does not hold. So a rewritten first row shows as a move from
  5 to 4, a sign of tampering. To get a pass, give the job the engine's key, or the keyless opt-out
  the engine runs under. A job in that setup that moves from 0 to 5 across this release is this
  change. See [SECURITY.md](../docs/SECURITY.md) "Tamper-evidence".
- `audit-verify` loads its settings as `audit-anchor` does, so a settings error is rendered by
  field and message and never stringified with the value it refused. Vault BACKLOG #3054.
