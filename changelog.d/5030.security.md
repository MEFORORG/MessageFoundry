- **A credential a generic ODBC connection string sends without braces is now hidden whole in a
  log line.** A password sent plain to a driver the engine has not measured, and every
  `odbc_params` value, `sslpassword` among them, may hold a space, `,`, `&` or, for a password,
  `=`. The log scrubbers stopped at the first three, so an echoed `;PWD=...;` would have printed
  the tail of the password, and `;sslpassword=...;` would have printed whole, since `ssl` glued to
  `password` gave the label no word boundary. A member right after a `;` whose key ends in a
  credential word or in `token`, such as `AccessToken`, now has its value taken to the next `;`,
  quote or line break, on the write-time log filters and in the support bundle and
  `GET /logs/tail`. It is a pass of its own that runs last of the credential passes, on both
  surfaces, so within one pass it only hides more of a line than before. The costs, at least:
  text after a glued `;password=` in prose or a URL's matrix parameters is hidden to the next `;`,
  quote or the end of the line, and a later label inside that span loses its label to the
  placeholder. What it leaves, at least: a credential that is the FIRST member, with no `;` before
  it, still prints its tail after a space; a key that holds a credential word but does not end in
  one, such as `ClientSecretValue`, is read as before; on the write-time chain a member glued into
  the same token as a percent-encoded HL7 run is taken with that run by the PHI pass first, so its
  tail after a space prints, as it did before; and on a path that redacts the same text twice, at
  least store error text and a record two handlers filter, a later label the first pass swallowed
  is no longer read by a filter that runs after it, which a review measured printing a value the
  scrubbers hid before on 19 lines of a 20,000-line fuzz. That last one is an open finding.
