- **A script the remote-debugging guard refuses is now audited, and it raises an alert.** Until
  now a refusal left one WARNING line in the log and nothing else. Under `serve`, the engine now
  reads the guard's count every 30 seconds. When scripts were refused since the last read, it
  writes one `remote_debug_refused` audit row and raises one `remote_debug_refused` alert. Each
  carries `count`, the number refused since the last one, and `total`, the number since the
  process started. The process that injects the scripts chooses how often it tries, so it gets
  at most one row and one alert in each 30 seconds. Neither carries the script's file name,
  which that process also chooses. The name stays in the WARNING line. The alert's `connection`
  is `remote_debug:refused`, with the engine process's label appended where several share a
  store. A rule can match `event_type = "remote_debug_refused"`. Nothing resolves the alert, so
  an operator does. Other commands, such as `supervise`, `rotate-key` and `backup`, hold no open
  store and still log the WARNING only.
  [SECURITY-LOOSENING.md](../docs/SECURITY-LOOSENING.md) has the detail, under
  `remote_debug_enabled`. (`vault BACKLOG #2742`)
