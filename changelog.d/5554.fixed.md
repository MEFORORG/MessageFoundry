- **`validate`, `graph` and `dryrun` evaluate the environment `--env` names.** They used the flag
  only for the value-file check under `--project-root`, and without `--project-root` it had no
  effect, so a gate given `--env prod` could exit 0 on a graph whose `env()` values `serve --env
  prod` cannot resolve. Given `--env`, they now run the service settings load `serve` runs, with
  `--env` as `[ai].environment` and `--project-root` as `[environments].base_dir`, then read the
  value file with `serve`'s reader, so overrides such as `MEFOR_VALUE_*` apply. That load also
  names the file the missing-value-file check looks for, which now fires under a `base_dir` from
  the settings file or the environment too, as it does for `serve`. Each `env()` reference of a
  deployed connection or lookup that does not resolve is reported by its key, never its value:
  `validate` lists it with its other problems, `dryrun` stops on it, and `graph` lists it under
  `env_problems` beside the graph without failing. Settings that do not load fail the command,
  naming the settings file, and so does a value file that cannot be read; an absent value file
  reads as no values, with a note naming it. With no `--env`, nothing changes. They build no
  connector, so at least the build and posture checks stay `check --env`'s. ADR 0050 records where
  they still differ from `serve`. (`BACKLOG #5554`)
- **A deeply nested service settings file is reported, not raised.** The settings load behind
  `serve`, `supervise` and the operator commands now reports the `RecursionError` the TOML parser
  raises on it, as it reports any other settings that do not load. (`BACKLOG #5554`)
