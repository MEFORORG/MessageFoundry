- **`validate`, `graph` and `dryrun` evaluate the environment `--env` names.** They used the flag
  only for the value-file check under `--project-root`, and without `--project-root` it had no
  effect, so a gate given `--env prod` could exit 0 on a graph whose `env()` values `serve --env
  prod` cannot resolve. Given `--env`, they now run the service settings load `serve` runs, with
  `--env` as `[ai].environment` and `--project-root` as `[environments].base_dir`, then read the
  value file with `serve`'s reader, so overrides such as `MEFOR_VALUE_*` apply. For `validate`
  and `dryrun` that load also names the file the missing-value-file check looks for, and the check
  now fires under a `base_dir` from the settings file or the environment too, as it does for
  `serve`; `graph` keeps the check it ran before, which still exits 2. Each `env()` reference of a deployed connection or lookup that does not resolve is
  reported by its key, never its value. Settings that do not load are reported as `serve` renders
  them, naming the settings file where one exists, and a value file that cannot be read is
  reported naming that file. `validate` lists these with its other problems and `dryrun` stops on
  them; `graph` lists them under `env_problems` beside the graph without failing. An absent value
  file reads as no values, with a note naming it. With no `--env`, nothing changes. They build no
  connector, so at least the build and posture checks stay `check --env`'s. ADR 0050 records where
  they still differ from `serve`. (`BACKLOG #5554`)
- **A deeply nested service settings file is reported by the shared settings load.** That load,
  behind at least `serve`, `supervise` and the offline commands under `--env`, now reports the
  `RecursionError` the TOML parser raises on such a file, as it reports any other settings that do
  not load. Other settings reads, at least `dryrun`'s `[pipeline].snapshot_on_send` read and
  `check`'s value-folder read, still raise it. (`BACKLOG #5554`)
