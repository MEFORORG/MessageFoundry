- **A `File(...)` source under `after_read` `move` or `delete` reaches healthy drops behind rejects it
  cannot quarantine.** A rejected file (oversize, a failed gunzip, a content-type mismatch, a scanner
  rejection) whose move to `.error` failed stayed in place and was read and charged against
  `poll_max_files` again on later scans, so enough of them sorting first could hold back the files
  behind them. When the move fails for a reason that looks lasting, such as access denied, a link or
  a missing `.error`, the source now remembers the file by path, size, modification time and file
  identity, and skips it unread and uncharged until one of those changes or 300 seconds pass, when it
  is read and tried again. The same holds when a copy was archived but the original could not be
  removed, so the copy is not written again on every scan. A reject still charges the scan that read
  it, so a scan reads at most `poll_max_files` files that end in a reject. A failure that looks
  transient (at least a locked file, a vanished file, a full disk or a dropped share) is not
  remembered, and such a file still charges on later scans. Scan-hook and handler failures still
  charge nothing. `after_read = "leave"` is unchanged, and so is `Sftp(...)`/`Ftp(...)`.
