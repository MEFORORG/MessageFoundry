- **A `File(...)` source under `after_read` `move` or `delete` reaches healthy drops behind rejects it
  cannot quarantine.** A rejected file (oversize, a failed gunzip, a content-type mismatch, a scanner
  rejection) whose move to `.error` failed stayed in place and was read and charged against
  `poll_max_files` again on later scans, so enough of them sorting first could hold back the files
  behind them. When the move fails for a reason that looks lasting, such as access denied, a link or
  a missing `.error`, the source now remembers the file and skips it unread and uncharged, at least
  until its size, modification time or file identity changes. After `STUCK_RETRY_SECONDS` it is
  examined again in full, after every other candidate in the scan and within a per-scan allowance:
  it is read and judged afresh, so a file that now passes is ingested, and one still rejected is
  charged and remembered again. A retry of a file copied into `.error` whose original could not be
  removed may write a second copy and record a second event. A failure that looks transient (at
  least a locked file, a vanished file, a full disk or a dropped share) is not remembered, and such a
  file still charges on later scans. Scan-hook and handler failures still charge nothing.
  `after_read = "leave"` is unchanged, and so is `Sftp(...)`/`Ftp(...)`. (`BACKLOG #5717`)
