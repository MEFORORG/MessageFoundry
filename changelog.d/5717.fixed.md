- **A `File(...)` source under `after_read` `move` or `delete` reaches healthy drops behind rejects it
  cannot quarantine.** A rejected file (oversize, a failed gunzip, a content-type mismatch, a scanner
  rejection) whose move to `.error` failed stayed in place and was read and charged against
  `poll_max_files` again on later scans, so enough of them sorting first could hold back the files
  behind them. When the move failed for a reason that does not clear by itself, such as access denied
  or a link, the source now remembers the file by path, size, modification time and file identity, and
  skips it unread and uncharged until one of those changes or the engine restarts. The same holds when
  a copy was archived but the original could not be removed, so the copy is no longer written again
  on later scans. A reject still charges the scan that read it, so a scan reads at most
  `poll_max_files` files that end in a reject. A failure that may clear by itself (at least a locked
  file, a vanished file, a full disk or a share timeout) is not remembered. Scan-hook and handler
  failures still charge nothing. `after_read = "leave"` is unchanged, and so is `Sftp(...)`/`Ftp(...)`.
  (`BACKLOG #5717`)
