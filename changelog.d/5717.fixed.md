- **A `File(...)` source under `after_read` `move` or `delete` reaches healthy drops behind rejects it
  cannot quarantine.** A rejected file (oversize, a failed gunzip, a content-type mismatch, a scanner
  rejection) whose move to `.error` failed stayed in place and was read and charged against
  `poll_max_files` again on later scans, so enough of them sorting first could hold back the files
  behind them. When the move fails for a reason that looks lasting, such as access denied, a link or
  a missing `.error`, the source now remembers the file by path, size, modification time and file
  identity, and skips it unread and uncharged until one of those changes. Every 300 seconds it tries
  the move alone again, unread and uncharged, and records the quarantine event if that works. When a
  copy was archived but the original could not be removed, the move is not retried, so no second copy
  is written. A reject still charges the scan that read it, so a scan reads at most `poll_max_files`
  files that end in a reject. A failure that looks transient (at least a locked file, a vanished
  file, a full disk or a dropped share) is not remembered, and such a file still charges on later
  scans. Scan-hook and handler failures still charge nothing. `after_read = "leave"` is unchanged,
  and so is `Sftp(...)`/`Ftp(...)`. (`BACKLOG #5717`)
