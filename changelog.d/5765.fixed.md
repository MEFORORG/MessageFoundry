- **A key-service outage during a claim no longer dead-letters the row or raises a false
  integrity alert.** On a `vault_transit` store, a queue payload that could not be opened because
  Vault gave no verdict (unreachable, a 5xx, a refused token) was read as the row failing its queue
  tag: the claim dead-lettered a healthy message and wrote an `integrity_drift` alert and audit row.
  Now that failure, a failed read of the store on SQLite, and a dead-letter write that fails are
  treated as infrastructure faults. Only the pooled FIFO claim, `claim_fifo_heads`, hands the row to
  the existing infra-fault path, which retries it with backoff and, if the fault lasts, stops the
  lane with a `connection_stopped` alert (`infra_fault_policy = "stop"`) or raises `lane_stuck`
  (`retry_forever`). Every other claim puts the row back to `pending` five seconds ahead, and it is
  retried with no cap and no alert of its own while the fault lasts. At least these claims do that: every claim
  under `claim_mode = "per_lane"`, an unordered outbound lane's claim under `pooled`, and the extra
  rows a batch window claims. A FIFO claim sets aside every later row it claimed with the row, and
  an unordered claim sets aside only that row. A tag failure whose dead-letter
  write fails is still audited and alerted. A refusal Vault did give a verdict on is dead-lettered
  and reported as before. (`BACKLOG #5765`, `BACKLOG #5735`)
