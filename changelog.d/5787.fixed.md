- **An upload with no closing boundary delimiter is refused.** A `multipart/form-data` upload body
  with no closing delimiter `--<boundary>--` was parsed, so a body that ended early was stored as a
  shorter file. It is now refused, with HTTP **400** where no size or part limit refuses it first.
  A boundary delimiter now counts only at the start of a line (at the start of the body, or after a
  CR or an LF), so delimiter text in the middle of a content line stays in the file, and a body
  whose only close marker sits mid-line is refused. A body whose first delimiter text does not
  start a line (a stray space or BOM before it, a preamble ending mid-line, or delimiter text
  mid-line in a preamble) is now refused with HTTP **400** where no size or part limit refuses it
  first. Such bodies were parsed before, though the upload route already refused some of them,
  with another message, for holding no file part or more than one. A line that starts with a
  delimiter and has anything after it other than spaces or tabs, or a close's `--` and then spaces
  or tabs, such as `--<boundary>note`, `--<boundary>--note` or `--<boundary>--epilogue`, is no
  longer read as a delimiter or as the close, and the body is refused the same way. Before, such
  a line in a file cut the file there, and a body built with a longer boundary than its
  Content-Type names was refused as truncated. Spaces or tabs after a delimiter are now skipped
  before the part's headers are read. A bare CR counts as the end of a line. A content line that
  is `--<boundary>` or `--<boundary>--` followed only by spaces or tabs is still read as a
  delimiter or as the close. (`BACKLOG #5787`)
