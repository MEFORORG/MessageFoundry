- **Per-connection `tls_ca_file` follow-ups.** A blank `env()` value for `tls_ca_file` is now
  refused when it resolves, naming the setting, the connection and the environment key. Before, it
  read as unset, so the hop would have trusted what it trusts with no pin. On the verifying paths
  the runner builds, a CA file that cannot be read now raises `CaFileUnreadable`, which names the
  setting and, where the build knows it, the connection. It is both a `ValueError` and an `OSError`;
  before, it was a bare `FileNotFoundError`. The text carries no path, because a connection test
  returns it to the caller. The inbound FTPS poller now reads the instance `[tls]` block, as the
  FTPS upload does, so `internal_ca_file`, `trust_anchor_mode` and `crl_file` reach it, and its
  warnings name it `inbound:<name>`. The token hop still shares the data hop's `tls_ca_file`, as
  [CONNECTIONS.md](../docs/CONNECTIONS.md#pinning-a-private-ca-per-connection-tls_ca_file) says.
  (`BACKLOG #2370`)
