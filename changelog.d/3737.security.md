- **`rotate-key` keeps a rotation record, and a `serve` start does not stamp a key while that
  record names it.** The command opens the record in `secret_rotation_meta` inside its store
  open, before that open's first write under the key (`BACKLOG #4936`), unless the store-key
  stamp already names the key the run moves to. When it opens one, a record already open for
  another key, or one that cannot be read, is replaced, keeping its dates; when it does not, any
  open record is left in place. The command closes the record only when a run gets through both
  data passes with no upload skipped and its audit roll does not refuse, and a run on the key
  already in use that gets that far closes an open record too. A closed record does not prove that
  nothing is left under the prior key; [PHI.md](../docs/PHI.md) names cases. A run that stops
  short leaves an open record open, and so does one killed inside the store open after the record
  opened. A run killed before that point opens no record and leaves any record already open,
  whoever opened it, as it was. When a start finds that the key in use differs from its stamp, has
  none, or has one under a scheme this release does not know, and the record names that key or
  cannot be read, `serve` writes no stamp, does not reset the key's age, and logs a WARNING. On a
  store with a keyed audit chain, a start holds such a key in at least two more cases. Where a
  record stands open for another key, the start keeps that record and holds the key. Where none is
  open and the open does not find the chain rolled to the key, the start opens the record for the
  key itself, unless it refuses to start because the key of the chain's current range is not
  configured (`BACKLOG #4934`). A store with a key whose audit rows open with no genesis row has no
  keyed chain: there the roll refuses on every run, so no run closes the record, and a record
  naming another key holds nothing, so a start stamps the key. The `BACKLOG #4942` entry says
  more. **Once a run
  has rolled a keyed audit chain to a new key there is no way back to the prior key**, and a run that skipped an uploaded file rolls like any other. **The upload
  pass opens only a regular file, and reads whole only one of a size an upload can be.** A FIFO no
  longer blocks it, a symlink is a skip and is not followed, and a file too large for an upload is a
  skip rather than an abort, unless it starts with the active key's marker, which reads as already
  current. Its log now says whether the key a skipped value names is configured. See
  [PHI.md](../docs/PHI.md). (`BACKLOG #3737`)
