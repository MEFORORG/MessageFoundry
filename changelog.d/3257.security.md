- **An attachment download refuses an `svg` start tag after leading text.** A body whose first byte
  past leading whitespace was not `<` was served as stored, even when it carried
  `<svg onload=...>` further on, under an SVG label too. Now the first 64 KiB past that leading
  noise is scanned for an `svg` start tag, plain or inflated from gzip, and the body is refused
  with a 422 when one is found. Only the tag counts, so a PDF, image or DICOM file that names the
  SVG namespace is still served. The download's pre-check reads the same bounded head, so a binary
  with no tag there skips the thread hop unless its leading noise runs past that head. Every such
  label was already served as an inert type with `nosniff`, so this is defence in depth, and what
  lies past the head rests on that inert-type allow-list, as
  [ADR 0105](../docs/adr/0105-streaming-very-large-hl7-attachments-detach-the-opaque-document-from-the-transformable-skeleton.md)
  records. The 422 now says the attachment carries SVG rather than that it is one.
