- **An attachment download refuses an `svg` start tag after leading text.** A body whose first byte
  past leading whitespace was not `<` was served as stored, even when it carried
  `<svg onload=...>` further on, under an SVG label too. It is now scanned for an `svg` start tag and
  refused with a 422 when one is found. A gzip body's inflated head, the first 64 KiB past leading
  noise, is scanned the same way. Only the tag counts, so a PDF, image or DICOM file that names the
  SVG namespace is still served. Every such label was already served as an inert type with
  `nosniff`, so this is defence in depth. The scan does not reach past a gzip body's head; that rests
  on the inert-type allow-list, as
  [ADR 0105](../docs/adr/0105-streaming-very-large-hl7-attachments-detach-the-opaque-document-from-the-transformable-skeleton.md)
  records. (`BACKLOG #3257`)
