- **A repeat reconciler revocation of one account is audited but not alerted.** In the shipped
  code, two reconcilers on one store could both revoke one account. Each wrote a row and raised an
  `ad_session_revoked` alert. For any reason but a scope change, each also sent the user a notice.
  The second ended nothing. Now a revocation that ended no session and changed no role still
  writes its `auth.ad_session_revoked` row, with `sessions: 0` (owner ruling 2026-10-16, "audit
  always"). When the directory says the account is disabled or absent, it still alerts and sends
  its notice, as when the user signed out mid-pass (owner ruling 2026-10-17). It is quiet only when
  another pass's row for the same username and reason was written after this pass started
  (`AuthService._already_revoked_elsewhere` states the rule). The pass tells by audit row id, read
  when it starts, not by `ts`, so another engine's fast clock cannot make an earlier row look like a
  repeat. A failed read of that id or of those rows is logged at ERROR and the revocation reports,
  so it still writes its row. Any
  other revocation that ends nothing is quiet. If both reconcilers read the old roles, or both
  apply before either writes its row, both still report. If the first reconciler's pass ended
  before it alerted, a repeat revocation now leaves the account paging nobody. Vault BACKLOG #3085,
  item 2.
