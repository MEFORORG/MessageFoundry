- **The SQL Server store pin takes the audited trust-anchor checks.** On SQL Server,
  `[store].ssl_root_cert` is sent as the ODBC `ServerCertificate` pin under `Encrypt=strict`, so
  it is the store hop's only trust anchor. It now joins the settings preflight under the label
  `store_sqlserver_pin`. A start that opens the store checks it, writing an `auth.trust_anchor`
  row at least for a first observation, a change or a finding, and every real reload checks it
  again (a dry-run reload runs no settings preflight);
  a file others can write refuses the reload at `[security].enforcement = enforce`. Those rows,
  and the baseline a change is judged against, travel the hop this pin secures, so a swapped pin
  can keep its own `changed` row out of the real store; the `store_sqlserver_pin` item of the
  `messagefoundry/auth/trust_anchors.py` module docstring says when, and which checks still
  refuse. The store's own check at each open stays,
  with no row, because it runs before the store is open; so a pin it refuses stops the start
  with no row: an ACL or path finding at `enforce`, and an unreadable file or refused content at
  either setting. A reload runs the
  anchor checks (the ACL, the path, a change, a file it cannot read) and the store's content
  checks, in the store's order: at least the encryption-header refusal (`BACKLOG #3090`), the
  private-key refusal (`BACKLOG #3745`), and that the file is one server certificate inside its
  validity period. So a pin past its notAfter is refused at least at every real operator, held
  and cluster-convergence reload and at DR activation until the file is replaced, and each
  convergence retry writes a `pem_refused` row. At `warn` a
  start logs the pin's warning once, not once per check. The store's check now reads the file
  once, so its certificate and anchor checks judge the same bytes. A pin file larger than 1 MiB
  is refused, naming the setting. Load reads at most that much. Store open checks the size on
  disk, then the bytes it read. A reload reads at most 1 MiB and one byte, and refuses a
  longer file with an audited row naming why. At start the store open refuses it first, with no
  row. At least the
  expiry monitor and `cert inventory` still read the file with no cap. (`BACKLOG #3714`)
- **A SQL Server pin beside a weakened store posture is refused at load.** With `encrypt = false`
  or `trust_server_certificate = true`, the store sends no pin, so a set `ssl_root_cert` used to
  be dropped with nothing said. Load now refuses that shape, as `ssl_crl_file` refuses its own.
  (`BACKLOG #3714`)
- **A trust-anchor refusal names what it refuses.** The ACL and path messages said a writer could
  "substitute the CA and defeat authentication", and ended "refuses to start" or "starting
  anyway", which was wrong for a dialling CA, the store pin and a reload. They now say a writer
  can substitute the anchor and defeat the TLS check that trusts it, and end "refuses it" or
  "using it anyway". (`BACKLOG #3714`)
