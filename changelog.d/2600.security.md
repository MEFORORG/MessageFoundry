- **A mistyped `MEFOR_<SECTION>_<KEY>` variable now refuses the load.** When the section has an
  env layer and the key is not real, `load_settings` raises, naming the variable and the nearest
  real one, never its value. It used to be dropped, so `MEFOR_STORE_REQUIRE_ENCRYPTON=true`
  started an instance without the hardening it asked for. Variables that are not settings and are
  read straight from the environment (the Vault, Transit, revocation-attestation and phase-timing
  names) are spared by an explicit list, and so is a variable that a setting names as a secret
  reference. **Not refused:** a variable whose section part matches no section with an env layer
  is still dropped in silence, and under `[secrets].provider = "env"` an unknown variable is
  warned about instead. **The check reads the whole process environment**, so a Kubernetes
  Service named `mefor-<section>` in the engine's namespace would stop the start through its
  service-link variables. See [CONFIGURATION.md](../docs/CONFIGURATION.md).
  (`vault BACKLOG #2600`)
- **Four `[auth]` switches are now reported loosenings when `false`:** `require_action_step_up`,
  `password_check_breached`, `password_check_context` and `password_check_username`. Each ships
  `true`, and nothing refuses one. The serve-time warning, `messagefoundry security show` and
  `GET /security/posture` name them. See
  [SECURITY-LOOSENING.md](../docs/SECURITY-LOOSENING.md). (`vault BACKLOG #2600`)
