- **The Direct destination's recipient trust check now refuses more than an untrusted issuer.**
  Construction used to check only that the `recipient_cert` was directly issued by a supplied
  `trust_anchor`. It now also checks that the issuing anchor is a CA and the recipient cert is
  not, the recipient cert's key usages where present, and that the recipient cert names every
  `recipients` address in its `subjectAltName`: an `rfc822Name` equal to the address, or a
  `dNSName` equal to its domain on a cert that names no `rfc822Name`. A cert naming any
  `rfc822Name` is bound to those mailboxes alone, so a cert the same CA issued to another
  subscriber, with or without a `dNSName` for that subscriber's domain, is no longer an
  encryption target. Both certificates' validity windows are read at
  every send: an expired or not-yet-valid one is a permanent configuration fault (code
  `direct-cert-validity:<setting>:<bound>`), which stops the lane and keeps the queue under the
  default `credential_fault_policy`.
  Construction only warns on the window, so check, reload and start still build the connection.
  What is checked, at
  least, is in
  [CONNECTIONS.md](../docs/CONNECTIONS.md#direct-project--direct-smime-over-smtp-outbound-send-adr-0085),
  *Recipient trust*. (`BACKLOG #5631`)
