- **A passkey sign-in whose passkey re-read raises would now be refused with an audit row, for the
  exception classes the read catches.** The account's passkeys are read again after the sign-count
  write and before the factor is marked. An exception there used to raise out of the ceremony with
  no `auth.webauthn_failed` row. Now a store or driver error the read catches is refused, the
  factor stays unmarked, the account and the exception's type are logged, and the row names
  `reason=store_error`. ADR 0068's amendment of 2026-10-17 lists, with an at-least, which classes
  are refused, which are re-raised first and which still raise. Those classes do not tell a store
  fault from a bug, so a bug that raises one is refused the same way. A bad statement is re-raised
  on SQLite, and on PostgreSQL and SQL Server it is a driver error and is refused as
  `store_error`. If the store refuses that row too, the refusal still comes back. Not covered, at
  least: the session, account and lock re-read beside it. (`BACKLOG #3775`)
