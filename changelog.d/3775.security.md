- **A passkey sign-in that meets a store fault in its passkey re-read would now be refused with an
  audit row.** The account's passkeys are read again after the sign-count write and before the
  factor is marked. A database driver error, a lost connection or a pool acquire timeout there
  used to raise out of the ceremony with no `auth.webauthn_failed` row. It is now logged and
  refused, the factor stays unmarked, and the row names `reason=store_error`. If the store
  refuses that row too, the refusal still comes back. On SQLite a bad statement raises
  `sqlite3.ProgrammingError`, which still raises; on PostgreSQL and SQL Server a bad statement is
  a driver error and is refused as `store_error` like any other. Which other faults in that read
  are refused, and which still raise, is listed in ADR 0068, amendment of 2026-10-17. Not covered,
  at least: the session, account and lock re-read beside it. (`BACKLOG #3775`)
