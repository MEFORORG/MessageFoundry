- **A passkey sign-in whose passkey re-read raises would now be refused with an audit row, for the
  exception classes the read catches.** The account's passkeys are read again after the sign-count
  write and before the factor is marked. An exception there used to raise out of the ceremony with
  no `auth.webauthn_failed` row. Now a `RuntimeError`, `OSError` or `ValueError` (a closed SQLite
  connection raises `ValueError`), SQLite's `DatabaseError`, asyncpg's errors, pyodbc's `Error`
  root or a pool acquire timeout is refused, the factor stays unmarked, the exception's type is
  logged, and the row names `reason=store_error`. Those classes do not tell a store fault from a
  bug, so a bug that raises one is refused the same way. If the store refuses that row too, the
  refusal still comes back. The defect classes in `AUDIT_WRITE_DEFECTS`, at least
  `sqlite3.ProgrammingError` (a bad statement on SQLite), are re-raised first, and every exception
  outside the caught classes, `sqlite3.InterfaceError` among them, still raises; on PostgreSQL and
  SQL Server a bad statement is a driver error and is refused as `store_error`. Not covered, at
  least: the session, account and lock re-read beside it. (`BACKLOG #3775`)
