- **The store now scrubs a captured reply's `detail`.** `complete_with_response` ran no scrub over
  `detail` on any backend, while an `ack_sent` row's `detail` went through `safe_text(detail,
  limit=200)`. Both row kinds now get that scrub and bound before the cipher, so the store is the
  chokepoint [PHI.md](../docs/PHI.md) names, whatever a connector puts in the field. At least the
  in-tree connectors' fixed phrases and status codes, such as `MSA-1=AA` and `HTTP 201`, pass it
  unchanged. The MLLP and X12 unparseable-reply details embed `safe_exc` text that was already cut
  at 200, so one near that bound is cut again here. Both methods now scrub before the SQLite writer
  lock, or the Postgres and SQL Server pooled connection and its transaction, is taken.
  `resp_headers` is deliberately not scrubbed, so a Handler reads back the values it was captured
  with. The connector's per-connection allow-list bounds which header NAMES are captured, not what
  their values hold: an allow-listed value, such as a `Location` naming a patient resource, is
  stored whole, and only the cipher covers it at rest. PHI.md now says so for each column and row
  kind. The item's fourth finding, that a value bounded twice carries a count note naming only the
  second cut, was reproduced and is kept: vault BACKLOG #3034 counts per call by decision, so the
  store never parses a count back out of text a peer can write. (`BACKLOG #2984`)
