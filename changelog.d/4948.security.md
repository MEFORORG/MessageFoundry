- **The mTLS issuer index reads a CA written under the legacy `X509 CERTIFICATE` PEM label, and
  a client CA file it cannot match to what the TLS library loaded now refuses the start.** The
  index names the loaded CA that issued a client certificate, for at least
  `[api].tls_client_cert_identities`, an inbound `Http` listener's `intake_client_subjects` and an
  inbound MLLP listener's `tls_client_subjects`. The TLS library loads the legacy label from the
  CA file each of them reads, so the handshake verified a client under such a CA, but the index
  read only `BEGIN CERTIFICATE` blocks. On a first deployment every client under that CA would
  have been refused, and the start warning would have said the issuer key named no loaded CA. A
  second CA with the same DN and a different key under the legacy label would have been missed
  too, so a client under the other one would have been admitted although the two cannot be told
  apart. The index now reads both labels, so two such CAs name no issuer, as with the standard
  label. The index also read a `CERTIFICATE` block nested inside a block of another label, such
  as a CRL, which OpenSSL skips whole, so a client that sent that nested CA as its intermediate
  would have verified through a CA OpenSSL did load and been named under the nested CA. It now
  skips such a body. **The index is now checked against the TLS library itself.** It finds the
  certificates by modelling OpenSSL's PEM reader, and that model still differs from OpenSSL on
  some shapes: OpenSSL silently stops loading a file at some blocks, such as an empty block, a
  label holding a `:`, or a blank body line before a data line over 64 characters, while the model
  reads on. So after the index is built, the same bytes are loaded into a scratch TLS context, and
  the start is refused, naming the setting, unless the CA certificates the index holds are exactly
  the ones that context lists, every other certificate the index holds is one the library reads as
  no CA, and it loaded as many of those. Such a certificate, a pinned client certificate for
  example, names only a client leaf that is that certificate, since OpenSSL never accepts it as
  the issuer of another. A certificate block `cryptography` cannot parse also
  refuses the start, where it was counted and skipped with a warning: at least one with an unknown
  version, bytes after its DER, or a NUL and more text in a base64 line, which OpenSSL loads.
  Skipped, such a CA left a same-DN twin with a different key looking unambiguous, so a client
  under the twin would have been named. A file the TLS library refuses, such as one with a block
  missing its END line, refuses the start as before. A CA with an unknown version raised out of
  the context build in the shipped code; the issuer lookup now names no issuer for a client leaf
  with one rather than raising.
  (`BACKLOG #4948`)
