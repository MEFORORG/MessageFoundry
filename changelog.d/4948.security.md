- **A client CA written under the legacy `BEGIN X509 CERTIFICATE` PEM label now names its
  partners.** The TLS context loads such a block, so the handshake verified a leaf under that CA,
  but the issuer index behind `intake_client_subjects` on the HTTP listener and
  `[api].tls_client_cert_identities` on the API read only `BEGIN CERTIFICATE` blocks. Every
  partner under that CA would have been refused, and the start warning said the key named no
  loaded CA rather than that a block went unread. The index now reads the two labels the context
  loads, only from a BEGIN line that is the marker alone, and checks each certificate it read, by
  itself, against a TLS context loaded from the same text: it is named only where that context
  holds it. A CA the context holds that the scan missed is taken from the context where
  `cryptography` can read it and every block `cryptography` refused can be matched to what OpenSSL
  loaded from it; a pinned certificate the scan missed is looked for under a marker anywhere on a
  line. A certificate set aside names no issuer, and a new start warning counts it. A block under
  either label that `cryptography` cannot parse still names no issuer, even where OpenSSL loads
  it, unless the same certificate is loaded from another block, and is still counted in the start
  warning. A certificate with a
  version field `cryptography` refuses no longer stops the index from being built. (vault BACKLOG
  #4948)
