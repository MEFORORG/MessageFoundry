- **A `serve` start no longer stamps a changed store key that the audit chain has not been rolled
  to.** On a store with a keyed audit chain, `rotate-key` rolls the chain only after both data
  passes, so a start that finds a changed key and a chain not yet rolled to it opens the rotation
  record for that key itself, writes no stamp, and logs a WARNING. A record already open for
  another key is kept rather than replaced, so that key stays held when it comes back. That covers
  a start before the first `rotate-key` run, a run killed inside the store open before it opened
  the record, and a key changed by hand. A store with no keyed chain to ask, such as one whose audit rows open with no
  genesis row, still stamps a changed key with no record. **A `rotate-key` audit step that refuses
  for good on a changed key now names ways out**, at least `[secret_rotation].store_key_last_rotated`
  and `[secret_rotation].enforce_store_key_expiry = false`. It does so when no run can roll the
  chain, as with a broken chain or one with no genesis row, and the rotation record stays open; a
  same-key run, and a refusal a re-run or a restored key clears, print no such note. See
  [PHI.md](../docs/PHI.md).
