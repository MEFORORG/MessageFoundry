- **A layered search refuses a blanked preset rather than widening, and no longer answers 500 on a
  cipher error reading a preset.** `GET /search/layered` read a preset whose stored criteria were
  NULL or empty as an empty filter, so a narrowing preset blanked outside the store dropped out and
  the search matched rows it would have excluded. The store now refuses such a cell on every
  backend, before the preset is stamped as used: it logs a WARNING, writes the
  `integrity.preset_tag_failed` audit row, raises the `integrity_drift` alert on a keyed store, and
  the route answers **423**. The WARNING, the row and the alert each fire at most once per preset
  and refusal class per hour in each engine process; the row's hour starts only once a write
  succeeds, so a failed write is tried again at the next refusal. The AlertSink's re-alert cooldown
  then applies per alert type and subject, and every preset refusal shares the subject
  `search_presets-tag`, so fewer notifications may reach the operator. A non-text cell, such as a planted BLOB, is refused the same way. It
  answered 500 on a keyed store, and on a keyless store it could be read as a filter. A cipher
  error on the preset's criteria that is not a failed tag, for example a value Vault Transit
  refused, answers **423** where it answered 500. It is logged at ERROR with the error's type name
  alone, once per preset and error class per hour in each engine process. A Transit outage answers **503** with
  `Retry-After`, as the upload routes do since `BACKLOG #3734`, and is logged at WARNING. A refusal
  while loading a stored preset, malformed criteria included, also tries to write the route's
  `preset.layered_search` audit row with the preset id, the status and the error class; that write
  is best effort. A cipher error on a message row the search then scans is not covered by this
  change. A layered search that returns rows now also feeds the coalesced `summary_access` audit,
  as `/messages/search` does. (`BACKLOG #5523`)
