## 3. High Availability, Failover & Disaster Recovery

**ID prefix:** `HA` · **Surface:** engine + infra (with web console / CLI / harness edges)
· **Primary risk:** a cluster that stops processing — or processes twice — with no page and no failing test, because the live PostgreSQL election suite and every live server-DB DR suite are wired into no CI leg and no alert fires when the cluster goes leaderless.

### 3.1 Scope & objectives

This chapter covers the **active-passive HA** model MessageFoundry actually ships: N engine nodes over **one shared server-DB store** (PostgreSQL or SQL Server), exactly one of which holds a self-fencing `leader_lease` row and runs the wired graph. Concretely:

- **Coordinator seam** — `ClusterCoordinator` Protocol, `NullCoordinator` (single-node byte-identical default), `DbCoordinator` (asyncpg), `SqlServerCoordinator` (aioodbc / `MERGE WITH(HOLDLOCK)`), and `build_coordinator` dispatch ([`pipeline/cluster.py:137-311`](../../../messagefoundry/pipeline/cluster.py), [`:326-983`](../../../messagefoundry/pipeline/cluster.py), [`:986-1058`](../../../messagefoundry/pipeline/cluster.py), [`pipeline/cluster_sqlserver.py:78-549`](../../../messagefoundry/pipeline/cluster_sqlserver.py)).
- **Election + fencing** — acquire-or-renew in one statement against the DB clock (`cluster.py:840-900`), the DB-free monotonic fence watchdog (`cluster.py:902-935`), the H1 leader-epoch token and its store-side claim guard (`store/postgres.py:2686-2688, 2816-2820, 2934-2938`; `store/sqlserver.py:796-802, 6003-6007, 6152-6156, 6320`), clean release on stop (`cluster.py:937-962`), ADR 0096 leader preference / non-promotable standby (`cluster.py:871-888`, `config/settings.py:2896-2910`).
- **Leader-gated work** — the graph supervisor (`pipeline/engine.py:1154-1268`), on-promotion in-flight recovery (`pipeline/leader_tasks.py:143-162` on PostgreSQL; `store.reset_stale_inflight()` on SQL Server, `engine.py:1177-1187`), the periodic expired-lease reclaim sweep (`leader_tasks.py:52-141`), leader-gated poll-source intake, and the leader-only WRITE singletons — retention, reclaim, DR backup (`engine.py:953-990`, `pipeline/dr_backup.py:257-259`).
- **Observability** — `GET /cluster/status` and `GET /cluster/nodes` (`api/app.py:4643-4698`), the derived single-live-leader projection (`cluster.py:555-604`), `leadership_acquired` / `leadership_lost` alerts (`cluster.py:966-983`, `pipeline/alert_sinks.py:98-104, 807-824`), and the web console status page's cluster/nodes/DR tables and `leaderless → health=down` derivation (`messagefoundry_webconsole/pages/monitoring.py:471-508`, `routes/status.py:58-97`).
- **Third-tier DR standby (ADR 0048)** — `DrCoordinator` activate/release, cold-seed restore-verify fail-closed, the BACKLOG #102 server-DB live-seed gate, the ADR 0102 restore-token vintage floor, the `dr_seed` audit-chain fork, acquire-VIP-or-abort hooks, the DR run-profile, and `POST /dr/activate|release` + `GET /dr/status` (`pipeline/dr.py:101-694`, `api/app.py:4700-4805`).
- **Turnkey DR backup (ADR 0049)** — `BackupRunner`, `.mfbak` archives, keep-N prune, `run_restore_verify` (`pipeline/dr_backup.py:135-560, 774+`) and the `messagefoundry backup` / `restore-verify` CLI (`__main__.py:604-656`).
- **HA packaging (ADR 0047)** — `docker/k8s/ha-postgres.yaml` (replicas 3, PDB `maxUnavailable: 1`, `terminationGracePeriodSeconds: 40` > the live `leader_lease_ttl_seconds` default) and the compose `ha` profile (`docker/compose.yaml:150-199`).
- **Cross-cutting proofs** — no-message-loss and bounded-duplicate delivery across a real failover, per-lane FIFO across a leadership change, RPO/RTO measurement, split-brain and partition behaviour, failback, and the harness failover orchestrator (`harness/load/failover.py`, `harness/load/failover_track.py`, `harness/load/profiles/failover.toml`).

**Objective.** Sign-off means: (a) every live HA/DR suite that exists actually runs somewhere on a schedule with recorded evidence; (b) a leaderless or two-leader cluster is detectable without a human staring at a page; (c) a numeric, gated RTO exists per backend; (d) no-loss and bounded-duplicate delivery across a failover is proven on both server DBs and re-proven across a *flap*, not just a single kill; (e) the DR cold-seed → activate → release → reconcile loop has an automated artifact, not only a runbook.

### 3.5 Detailed scenarios

#### S-HA-A — DB container restart mid-load (HA-10, HA-11)

**Preconditions.** Docker available; the `postgres:16` (or SQL Server 2022) service run as a *named* container the test can restart — a GitHub Actions `services:` container **cannot** be restarted from a step, so this leg must start its own container with `docker run --name mefor-ha-db` rather than use the `services:` block. Free loopback ports per `tests/_failover_load_support.py::reserve_failover_ports()` (6 ports: 3 inbound hubs, 1 sink, 2 API). Synthetic corpus only.

**Steps.**
1. `docker run -d --name mefor-ha-db -e POSTGRES_PASSWORD=mefor -e POSTGRES_DB=messagefoundry -p 5432:5432 postgres:16` and wait for `pg_isready`.
2. Export `MEFOR_STORE_BACKEND=postgres MEFOR_STORE_SERVER=localhost MEFOR_STORE_PORT=5432 MEFOR_STORE_DATABASE=messagefoundry MEFOR_STORE_USERNAME=postgres MEFOR_STORE_PASSWORD=mefor MEFOR_STORE_ENCRYPT=false MEFOR_ALLOW_INSECURE_TLS=1` (the plaintext-TLS escape the existing `postgres-store` job already uses).
3. Start the two-node cluster via the failover orchestrator's node spawner with a profile whose `[load.failover]` sets `heartbeat_seconds = 1.5`, `leader_fence_timeout_seconds = 3.0`, `leader_lease_ttl_seconds = 5.0`. **Do not** export `MEFOR_CLUSTER_*` yourself — the orchestrator sets them from the profile (`harness/load/failover.py:727-731`); operator values are inert (`W25:S5.3`).
4. Drive the sustained phase. At 40% into it, run the outage: **short arm** `docker pause mefor-ha-db; sleep 1.0; docker unpause mefor-ha-db`; **long arm** `docker stop mefor-ha-db; sleep 15; docker start mefor-ha-db`.
5. Let the load finish, then drain.

**Observation point.** Both nodes' captured stdout (use `MEFOR_BENCH_KEEP_NODE_LOGS=<dir>` so `EngineNode` persists `<node_id>.log` instead of unlinking it — `harness/load/failover.py`, proven by `tests/test_failover_keep_node_logs.py`); `GET /cluster/status` sampled every 200 ms on both API ports; the final `FailoverReport` JSON.

**Expected result.** Short arm: no `SELF-FENCED` line in either log, `max_concurrent_leaders <= 1`, leadership unchanged, listeners never unbound. Long arm: exactly one `SELF-FENCED` WARNING; both nodes report `role="standby"` for the outage window (cluster leaderless — this is the state HA-22's alert must catch); exactly one leader within `leader_lease_ttl_seconds + heartbeat_seconds` of DB readiness; `acked_not_delivered == 0`; `in_pipeline == 0` and `dead == 0` after drain.

**Cleanup / rollback.** `docker rm -f mefor-ha-db`; delete the node-log dir; the store is disposable. Nothing is written outside the scratch dir — in particular, the node logs may contain synthetic message metadata and must never be uploaded as a CI artifact without the standard load-report handling.

#### S-HA-B — Flapping failover, kill A → kill B (HA-12, HA-13)

**Preconditions.** As S-HA-A but with the DB left running throughout. A new profile `harness/load/profiles/failover-flap.toml` extending the shipped `failover.toml` shape with a second kill point.

**Steps.**
1. Extend `[load.failover]` parsing (`harness/load/profile.py:115-132`) so `kill_at_fraction` accepts a sequence, or add `second_kill_at_fraction`. The orchestrator's kill routine (`failover.py:566-612`) then performs a second SIGKILL after the survivor has been promoted **and** functional recovery has been observed — never before, or the second kill measures nothing.
2. Sustained phase 40 s at 40 msg/s, kills at 0.35 and 0.70.
3. After the second kill the first node must be **restarted** (a two-node cluster with both dead cannot re-elect) — the orchestrator restarts node A immediately after killing B, and A re-promotes by taking over the expired lease.

**Observation point.** `LeadershipTracker` samples across the whole run; the store-pool acquire-wait metric on each promotion; the final report.

**Expected result.** `max_concurrent_leaders <= 1` with `leader_samples > 0` across every transition; `acked_not_delivered == 0`; `lane_inversions == 0` over `lanes_observed >= 2`; `dup_rate <= max_dup_rate`; the pool acquire-wait p99 during the second promotion is within 2× the first. A regression in `_fire_pool_warm`'s orphan-cancel (`engine.py:1211-1224`) shows as a doubled acquire-wait and a stalled `recover_on_promotion`.

**Cleanup / rollback.** Orchestrator-owned; both `serve` subprocesses are terminated in its `finally`. Truncate `nodes` and `leader_lease` before the next run (the live suites already do this — `tests/test_cluster_failover_postgres.py:55-60`).

#### S-HA-C — Prove a leaderless cluster pages someone (HA-22, HA-06)

**Preconditions.** Two-node cluster on a live server DB; an alert rule targeting the new `cluster_leaderless` type routed to a capture sink; `[cluster].leader_lease_ttl_seconds = 5.0`.

**Steps.**
1. **Arm 1 — no eligible successor.** Bring up node A (`promotable=true`) and node B (`promotable=false`). SIGKILL A mid-load.
2. **Arm 2 — all non-promotable.** Cold-start both nodes with `promotable=false`.
3. **Arm 3 — DB gone.** Both nodes `promotable=true`; `docker stop` the DB for `4 × leader_lease_ttl_seconds`.

**Observation point.** The alert capture sink; `GET /cluster/status` on the surviving node(s); `GET /ui/nav-status` health verdict; the engine logs.

**Expected result.** In all three arms, exactly one `cluster_leaderless` alert opens within the configured N × TTL window and does not re-fire per tick; `/ui/nav-status` reports `health="down"` with reason `"cluster has no leader"`; in arm 2 an additional startup WARNING names the all-non-promotable misconfiguration (HA-06). When a promotable node is restored, the alert auto-resolves on the next `leadership_acquired`. **Today all three arms are silent** — that is the failing baseline this scenario must first reproduce before the alert is built.

**Cleanup / rollback.** Restart the DB; reset `promotable` to `true`; truncate `nodes` and `leader_lease`; clear the alert store rows created by the run.

#### S-HA-D — Kubernetes leader-pod delete and PDB drain (HA-41, HA-42, HA-44)

**Preconditions.** A `kind` cluster in CI. A config-baked image built from the repo's Dockerfile with a minimal synthetic graph (one MLLP inbound, one Router, one Handler, one file outbound) — **not** a real feed config. An in-cluster Postgres (a plain Deployment is acceptable for the drill; `docs/CLOUD-DEPLOYMENT.md` requires a managed DB for production, which this leg is not). `docker/k8s/ha-postgres.yaml` applied with `image:` and `MEFOR_STORE_SERVER` substituted, and — because the drill runs plaintext in-cluster — the TLS-exposure guards satisfied per the manifest's own env block or the leg pinned to loopback binds.

**Steps.**
1. `kubectl apply -f <rendered manifest>`; wait for 3/3 ready.
2. Identify the leader: poll each pod's `GET /cluster/status` for `role == "primary"`.
3. Start synthetic MLLP load through the Service.
4. `kubectl delete pod <leader>` (normal deletion → SIGTERM → `terminationGracePeriodSeconds: 40`).
5. Sample `/cluster/status` on all pods every 200 ms until a new `primary` appears; record the interval.
6. Separately, `kubectl drain <node hosting the leader> --ignore-daemonsets --delete-emptydir-data` and observe the PDB.

**Observation point.** The `/cluster/status` sample series; `kubectl get pdb`; the deleted pod's terminal log lines (it must log the clean lease release before exiting); `SELECT lease_expires_at FROM leader_lease` read directly during the grace window.

**Expected result.** A successor reports `primary` within `terminationGracePeriodSeconds` — and in practice within one heartbeat, because the clean stop expires the lease at once (`cluster.py:948-953`). No sample shows two `primary` pods. `acked_not_delivered == 0`. Under drain, `kubectl get pdb` shows `ALLOWED DISRUPTIONS: 0` while an eviction is in flight, i.e. never more than one replica down. A TCP connect to a standby pod's MLLP port is **refused** (HA-44).

**Cleanup / rollback.** `kind delete cluster`. No persistent volumes survive; no image is pushed to a registry.

#### S-HA-E — Cross-store DR fail-back reconciliation (HA-45)

**Preconditions.** Two independent stores: "primary" and "DR". A verified `.mfbak` cold-seed archive produced by `messagefoundry backup` on the primary. An env-sourced DEK reachable from both (`MEFOR_STORE_ENCRYPTION_KEY`) — DPAPI is machine-bound and will not work here (`FCP:DR-19`, §18). `[dr].enabled = true` on the DR box; `[cluster].enabled` must be **false** there (the mutual-exclusion validator, `settings.py:3722-3740`).

**Steps.**
1. Drive N synthetic messages into the primary; let them reach `PROCESSED`. Capture the primary's dispositions with `python -m harness.reconcile capture` pointed at a sink, or read control ids from `/messages`.
2. Stop the primary abruptly (simulated site loss).
3. On the DR box: `POST /dr/activate` with `{"archive": "<path to .mfbak>"}` (plus `"dba_attests_restored": true` on a server-DB store). Confirm 200, `verify_status="PASS"`, and a `dr_seed` audit segment.
4. Drive M further synthetic messages at the DR box's priority-tier Connections.
5. Restart the primary. `POST /dr/release` on the DR box; confirm the drain completes and `active=false`.
6. Run the new reconcile step: `python -m harness.reconcile compare --dr-failback --mefor <DR capture> --primary <primary capture> --report-json <out>`.

**Observation point.** The reconcile report JSON.

**Expected result.** The report enumerates three disjoint sets by control id — DR-only, primary-only, both-sides — with counts, and exits non-zero because M messages exist only at DR. The clean control case (activate then immediately release with no traffic) exits zero with all three sets empty. **The report must carry control ids, counts and dispositions only — never message bodies.**

**Cleanup / rollback.** Delete both stores and the `.mfbak`. `POST /dr/release` must have been called, or the DR box remains active and will keep binding priority feeds; verify `GET /dr/status` shows `active=false` before teardown.

#### S-HA-F — Always On AG forced failover and the stranded-in-flight remedy (HA-36, HA-39)

**Preconditions.** An AG lab: ≥2 SQL Server replicas, a WSFC with a quorum witness, an AG listener, and the `mefor` database in the AG with the prerequisites at `AOAG-DEPLOYMENT.md` §4.4. Two engine nodes clustered against the listener DSN. Sustained synthetic load. **Environment-blocked if the lab does not exist** — see open question 4.

**Steps.**
1. Baseline: record `heartbeat_seconds`, `leader_fence_timeout_seconds`, `leader_lease_ttl_seconds` and the AG's measured failover time.
2. Under load, perform a **planned** failover from SSMS (`ALTER AVAILABILITY GROUP … FAILOVER`).
3. Under load, perform a **forced** failover with data loss on the secondary.
4. After each, run the §8 stuck-in-flight check.
5. If in-flight rows are stranded, restart the active engine service (`Restart-Service`), which releases the lease cleanly and triggers on-promotion `reset_stale_inflight`.

**Observation point.** Engine logs on both nodes (search for `SELF-FENCED` and `acquired leadership`); the in-flight row count before and after the service restart; the harness report.

**Expected result.** Planned failover (typically well under the fence margin): documented behaviour is no fence and no leadership change. Forced failover: whichever behaviour occurs is *recorded against the §5.2 prediction* — the objective here is to falsify or confirm the doc, not to assert a fixed outcome. In all cases `acked_not_delivered == 0`; every stranded in-flight row is re-pended by the restart and subsequently delivers. Any divergence from `AOAG-DEPLOYMENT.md` §5.2/§5.3 is filed as a doc defect.

**Cleanup / rollback.** Fail back to the original primary; re-seed the secondary if the forced failover left it needing resume; drain and truncate the synthetic store.

#### S-HA-G — Engine shard × `[cluster]` lease collision (HA-03)

**Preconditions.** A config with ≥2 declared engine shards (per ADR 0037), one shared PostgreSQL store, `[cluster].enabled = true`.

**Steps.**
1. Start `python -m messagefoundry serve --config <cfg> --shard A` and `… --shard B` against the same store and schema.
2. Poll both API ports' `GET /cluster/status`.
3. Read `SELECT lease_key, owner FROM leader_lease` directly.
4. Send synthetic traffic to an inbound Connection owned by engine shard B.

**Observation point.** The two `/cluster/status` responses; the single `leader_lease` row; whether engine shard B's inbound port accepts a connection.

**Expected result (today, to be reproduced first).** One `leader_lease` row with `lease_key = 'public:mefor_cluster_leader'` (`cluster.py:414`); exactly one process reports `role="primary"`; engine shard B binds nothing and its traffic is refused — a **silent full stop for that engine shard** with a healthy-looking cluster status. **Expected after the fix**, whichever the owner chooses: either config load fails with an explicit "engine shards and `[cluster]` cannot be combined" error, or `lease_key` incorporates the engine-shard id so each engine shard elects its own leader and both bind.

**Cleanup / rollback.** Stop both processes; `TRUNCATE nodes, leader_lease RESTART IDENTITY CASCADE`.

#### S-HA-H — Backup to a UNC share under the NSSM service identity (HA-53)

**Preconditions.** The Windows Server 2025 box (`WIN-NAFGLU5SH1J`) running the engine under its production NSSM service account. A real UNC share the account can be granted (or denied) write rights on. `[backup].enabled = true`, `destination = \\<host>\mefor\backups`, `retention_keep = 3`, `schedule_at` set a few minutes ahead. Synthetic store only — never a PHI instance.

**Steps.**
1. **Negative arm first.** Remove the service account's write right on the share, restart the service, and read the startup preflight output.
2. Grant write rights; restart; wait for the scheduled window.
3. Force four successive passes (adjust `schedule_at`, or drive `messagefoundry backup --destination \\<host>\mefor\backups`) so keep-N prune has something to prune.

**Observation point.** The engine log at startup (preflight); the share's directory listing; the `dr_backup` audit rows via `GET /audit` or the console.

**Expected result.** Negative arm: the preflight **warns and does not raise** (the documented `FCP:DR-9` behaviour) and the log names the unwritable destination. Positive arm: each pass writes one `.mfbak`, records one PHI-free `dr_backup` audit row, and after the fourth pass exactly 3 archives remain, the oldest pruned. A verify-failed archive is never counted as one of the kept 3.

**Cleanup / rollback.** Delete the archives from the share; reset `[backup].enabled = false`; restore the original share ACL.

- **A second "DR site" host** with an independently restored store, plus a DBA who can perform and attest a native restore — HA-48's negative arm can be simulated in CI, but HA-50/HA-51 cannot.

**Accounts, keys and shares.**
- A **service account** with (and, for the negative arm, without) write rights on a real **UNC share** — HA-53. No cloud destination is permitted: `[backup].destination` and `[dr].seed_archive` reject cloud URLs by validator (`settings.py:3223-3224`, `:3396-3404`).
- An **env or external KeyProvider** reachable from the DR site (`MEFOR_STORE_ENCRYPTION_KEY`, KMS/Vault/HSM) — DPAPI is machine-bound and will fail cross-box by design (HA-50).
- `MEFOR_STORE_PASSWORD` in the self-hosted runner's machine environment (already the case).
- An **SMTP relay** and/or a **webhook sink** for HA-26.
- **NTP-synced clocks** on every cluster node (HA-16) — a documented assumption for the wall-clock per-row leases.

**Ports and capacity.**
- The failover orchestrator reserves **6 free loopback ports** (3 inbound MLLP hubs, 1 correlation sink, 2 API) via `reserve_failover_ports()`. On the W2025 box use `--inbound-base-port 2600 --sink-port 2700` per `W25:S4.9`.
- CI budget: the two existing failover legs each carry `@pytest.mark.timeout(180)` with two reruns on two backends. The new chaos and k8s legs roughly double that; they belong on the nightly schedule, not the PR path.

**Test data — synthetic only.**
- All traffic comes from the harness's own generated corpus (`harness/load/corpus.py`) or `messagefoundry generate`. No real PHI in any scenario in this chapter.
- **`dryrun` and `generate` output can contain full message bodies** — never redirect either into a committed file, a ticket, or a CI log.
- Failover and reconcile reports carry counts, seconds, node ids, control ids and SLO verdicts only. HA-28 makes that a test, not a convention.
- Node logs captured via `MEFOR_BENCH_KEEP_NODE_LOGS` are treated as the same class as load reports: scratch-dir only, never committed, never uploaded without review.

### 3.8 Exit criteria

This area is signed off for release when **all** of the following hold and are recorded with dated evidence:

1. **Zero never-run live suites.** `tests/test_cluster_failover_postgres.py` and all six live server-DB DR/backup files (`test_dr_server_seed_gate_{postgres,sqlserver}.py`, `test_dr7_server_config_only_backup_{postgres,sqlserver}.py`, `test_backup_runner_server_db_{postgres,sqlserver}.py`) each appear in a named CI job step and have reported PASS — not SKIPPED — in at least three consecutive nightly runs. (HA-01, HA-02.)
2. **A leaderless cluster is loud.** All three arms of S-HA-C open exactly one alert and produce `health="down"`; the all-non-promotable case additionally logs a named startup warning. Or: the owner records a formal, dated risk acceptance in the master plan and in `docs/CLUSTERING.md`. (HA-22, HA-06.)
3. **The engine-shard × `[cluster]` interaction has a decided, tested semantic** — either a config-load rejection or an engine-shard-namespaced lease key — and `tests/test_cluster_shard_interaction.py` asserts it. (HA-03.)
4. **An absolute RTO number exists per backend.** `max_promotion_seconds` and an absolute `functional_recovery_seconds` bound are set for the declared reference runner, gated in CI, and the current values are published in the release notes. A Windows figure from `W25:S4.9` (with `port_rebind_seconds`) is recorded alongside as host-specific. (HA-29, HA-30, HA-31, HA-34.)
5. **No-loss and bounded-duplicate delivery survive a flap, not just a kill.** The multi-kill profile passes all six SLOs on both server DBs. (HA-12.)
6. **A DB restart mid-load is a passing automated leg** on both server DBs, with the short-arm/long-arm fence behaviour matching `AOAG-DEPLOYMENT.md` §5.2 (or the doc corrected). (HA-10, HA-11.)
7. **The multi-node `/cluster/nodes` projection is asserted live** through register → heartbeat → promote → clean-stop on both server DBs, and the web console's leaderless derivation is exercised against a real cluster. (HA-23, HA-24.)
8. **The PostgreSQL coordinator has a live primitive suite** (`tests/test_postgres_coordinator.py`) at parity with the SQL Server one, including `cluster_members` derivation and `config_version` convergence. (HA-04, HA-62.)
9. **The k8s HA manifest is proven as behaviour, not shape** — leader-pod delete promotes a successor inside the grace window with zero acked loss, the PDB holds under drain, and standby pods refuse MLLP. Or: `ha-postgres.yaml` is explicitly re-labelled lint-only in ADR 0047 and the master plan. (HA-41, HA-42, HA-44.)
10. **DR fail-back has an artifact.** The reconcile step exists, is documented in the DR runbook, and its integration test passes. (HA-45.)
11. **A full HTTP `activate → release` round trip passes**, both audit-chain segments verify independently, and the #102 gate is proven live to refuse a fresh server DB even when attested. (HA-46, HA-47, HA-48.)
12. **HA correctness is on the merge path.** The `serverdb` path filter covers `pipeline/engine.py`, `leader_tasks.py`, `dr.py`, `dr_backup.py` and the DR/failover test files; the rerun rate of the two load-failover legs is visible per run; a required-check decision is recorded. (HA-32, HA-33.)
13. **The AG position is explicit.** Either the drills (HA-36, HA-37, HA-39) are executed on a lab with recorded evidence, or the master plan states, dated, that Always On AG behaviour is documentation plus a manual drill checklist with no lab — and `docs/AOAG-DEPLOYMENT.md` carries the same statement.
14. **DR readiness is assertable on the box.** `harness/acceptance/matrix.py` has DR rows, `WIN2025-TEST-MATRIX.md` §G has a DR row, and `messagefoundry verify` has a cluster and a DR section — or each is dispositioned as deferred with a named owner. (HA-54, HA-55.)
15. **Catalogs are truthful.** `FEATURE-MAP.md` §6 names every Accepted HA/DR ADR (guarded by the MIG FEATURE-MAP drift-guard row extending `tests/test_feature_map_claims.py`); `FCP:HA-20` and `FCP:DEPLOY-26` are corrected; BACKLOG #100 and #101 read SHIPPED. (HA-57, HA-58, HA-59.)

### 3.9 Open questions

1. **Are the never-run live suites wired into CI, or accepted as local-only pre-release runs?** `tests/test_cluster_failover_postgres.py` and the six live server-DB DR/backup files exist and pass, but no workflow invokes them. Wiring is a handful of YAML lines reusing env already present in `postgres-store` / `sqlserver-store`. *Blocks:* HA-01, HA-02, HA-48, HA-56 — and, transitively, exit criteria 1 and 11. If the answer is "local-only", who runs them, on what cadence, and where is the evidence recorded?
2. **Should a `cluster_leaderless` alert be built, or is a leaderless cluster a formally accepted silent risk?** Today `leadership_lost` is auto-resolve-only by deliberate design (`alerts.py:206-213`) and the alert-type set has no "no leader" member. A fully fenced, all-non-promotable, or DB-less cluster stops processing and pages nobody. *Blocks:* HA-22, HA-06, exit criterion 2.
3. **What are the target RPO and RTO per backend and per topology** — single-site HA, AG, third-tier DR? Recovery is bounded today only relative to whatever lease TTL a profile happens to set, and no RPO figure is asserted anywhere in the repo. *Blocks:* HA-29, HA-30, exit criterion 4, and the numbers the release notes quote.
4. **Is an Always On AG lab available or fundable?** If not, AOAG stays 919 lines of documentation plus a manual drill checklist, and the master plan should say so explicitly rather than carry HA-36/HA-37/HA-38/HA-39/HA-40/HA-51 as open gaps. *Blocks:* exit criterion 13.
5. **Is a Kubernetes cluster available for a real leader-pod-kill / PDB-drain leg,** or does `ha-postgres.yaml` stay lint-only (structural assertions with no deployed behaviour)? *Blocks:* HA-41, HA-42, HA-43, HA-44, exit criterion 9.
6. **What is the intended semantic when engine shards and `[cluster].enabled` are combined?** `_lease_key` is not engine-shard-namespaced (`cluster.py:414`) and no validator relates the two, so N-1 engine-shard processes would silently bind nothing. Reject at config load, or namespace the lease key per engine shard? *Blocks:* HA-03, exit criterion 3. **This is a newly identified P0 not present in the recon inventory.**
7. **Should an all-non-promotable cluster become a hard config/startup error, a startup warning, or a degraded `/cluster/status` signal** — or does the current "documented, not guarded here" stance (`settings.py:2905-2907`) stand? *Blocks:* HA-06.
8. **Who owns the cross-store DR fail-back reconciliation runbook step, and should `harness/reconcile` be productized as the supported tool for it?** `pipeline/dr.py:296-301` explicitly defers to an operator runbook that does not name a tool. *Blocks:* HA-45, exit criterion 10.
9. **Is `ack_after=delivered` still planned?** It materially changes the RPO story — today the ACK means receipt-and-persistence only — and would add an entire failover-behaviour dimension to this matrix. *Blocks:* the RPO statement in question 3, and whether this chapter needs a second no-loss dimension.
10. **Are flaky-tolerant (`reruns=2`), path-gated, non-required HA legs acceptable,** or should the failover legs become required checks with tracked rerun rates? *Blocks:* HA-32, HA-33, exit criterion 12.
11. **Should the self-hosted W2025 leg re-add `tests/test_cluster_failover_sqlserver.py`** (excluded at `selfhosted-win2025-sql.yml:77-83` for a documented VM hang)? Is real-Windows whole-lifecycle failover in scope for this release? *Blocks:* HA-35.
12. **Is ADR 0056 (engine-managed VIP + `POST /cluster/stepdown` + a console HA page) in scope for this release,** or does the master plan carry it as a recorded "design-only, not a test gap" disposition — as `FCP:HA-17`/`FCP:HA-18` already do? *Blocks:* whether HA-52's manual VIP drill is the permanent answer or a stopgap.
13. **Should FEATURE-COVERAGE-PLAN §16/§18 remain the per-row audit with this chapter citing it,** and are the corrections in §3.2 (`FCP:HA-20` false, `FCP:DEPLOY-26` self-inconsistent, FEATURE-MAP §6 omissions, BACKLOG #100/#101 stale) made in those documents before this chapter is finalized, or carried here as a correction list? *Blocks:* HA-57, HA-58, HA-59, exit criterion 15.
