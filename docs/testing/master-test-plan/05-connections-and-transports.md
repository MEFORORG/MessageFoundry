## 4. Connections & Transports Matrix

**ID prefix:** `CONN` · **Surface:** engine (`messagefoundry/transports/`) with CI-leg, harness and W2025-box legs
· **Primary risk:** the shared frame decoder treats a start byte **inside an open frame** as ordinary payload ([`framing.py:102-126`](../../../messagefoundry/transports/framing.py)), so a peer that aborts mid-frame and re-syncs by re-sending SB has two clinical messages silently concatenated into one — wrong clinical content downstream **and** a count-and-log record of one received message instead of two, with no error, no `ERROR` disposition and no connection event.

### 4.5 Detailed scenarios

#### S-CONN-A — The frame-merge defect: reproduce, decide, pin (CONN-01, CONN-02, CONN-03, CONN-05)

**Preconditions.** Any dev PC with the engine installed. No engine running; no store touched. Everything here is a pure decoder exercise plus one loopback socket — no PHI, no partner.

**Steps.**
1. Reproduce the merge in isolation first, so the decision is made against observed behaviour rather than a reading of the source:
   ```
   python -c "from messagefoundry.transports.mllp import MLLPDecoder; d=MLLPDecoder(); print(list(d.feed(b'\x0bMSH|A\x0bMSH|B\x1c\r')))"
   ```
   Record the output verbatim. Expected today: a single payload `b'MSH|A\x0bMSH|B'` — two messages merged, one yielded.
2. Repeat against the STX/ETX preset to confirm the behaviour is in `FrameDecoder`, not in the MLLP binding:
   ```
   python -c "from messagefoundry.transports.framing import STX_ETX_CODEC as C; print(list(C.decoder().feed(b'\x02A\x02B\x03')))"
   ```
3. Now show the **pipeline** consequence, which is the part that matters. Start a scratch engine on a throwaway store: `python -m messagefoundry serve --config samples/config --db <scratch>/conn-frame.db --env dev`. Open a raw socket to the MLLP inbound and write, in one `send`, `SB + <synthetic ADT #1 without EB> + SB + <synthetic ADT #2> + EB + CR`. Generate both messages with `messagefoundry generate` into a scratch directory — never a committed path.
4. Read `GET /messages` (or the `/ui` results table). Count the received rows.
5. Fetch the single stored raw and confirm message #2's segments are trailing segments under message #1's MSH.
6. **Take the decision (Q1).** The two candidates are: (a) *re-sync on SB* — an SB inside an open frame discards the partial buffer and starts a new frame, matching most tolerant HL7 receivers and yielding message #2 intact with message #1 lost-and-logged; (b) *status quo, documented* — SB is payload, and the plan carries an explicit accepted-risk entry. Option (a) changes both message counts and clinical content on a mid-frame abort, so it is an owner call, not an implementer's.
7. Write `tests/test_framing_resync.py` pinning whichever semantic is ratified, parametrized over both codecs, plus the CONN-03 truncate-then-reconnect case and the CONN-05 post-raise reuse case.
8. Add the CONN-02 fuzz corpus in the same module with a fixed seed so failures reproduce, and assert the three invariants rather than exact outputs.

**Observation point.** The decoder's yielded payload list in steps 1-2; the received-message **count** and the stored raw in steps 4-5; the new test module's pass/fail in steps 7-8.

**Expected result.** Steps 1-2 reproduce the merge on both codecs. Step 4 shows **one** received message where a partner sent two — the count-and-log invariant is violated silently. After step 7 the ratified semantic is the only one the suite accepts.

**Cleanup / rollback.** Stop the scratch engine; delete the scratch store and the generated corpus. Never point this at a real store. `generate` output can contain full bodies — keep it in the scratch directory and out of any commit, ticket or CI log.

### 4.9 Open questions

1. **Should `FrameDecoder` re-sync on a start byte seen inside an open frame, or is SB-as-payload the intended tolerant-receiver semantic?** `framing.py:117-126` only closes a frame on `byte == end`, so a peer that aborts mid-frame and re-sends SB has both messages concatenated into one — wrong clinical content downstream and one received message counted where two arrived. *Blocks:* CONN-01's pass criteria and, transitively, CONN-02/03/05. This is the chapter's only P0 defect and the answer changes both message counts and clinical content.
2. **`capture_connection_errors=True` is accepted for X12, DIMSE and HTTP inbounds (`wiring.py:3116-3122`) but only MLLP, TCP and the HTTP listener emit — wire X12 and DICOM SCP to the sink, or narrow the guard at `:3147` and fail loud?** Note the guard's own message already reads "only valid for an MLLP/TCP listen source" while `listens` includes three more types. *Blocks:* CONN-11's direction.
3. **Should `pipeline/cert_expiry.py` monitor SOAP `client_cert_file` and Direct `signing_cert` / `recipient_cert`?** `signing_cert` is the engine's own and is clearly in scope; `recipient_cert` is a **partner-held** certificate — is proactive expiry alerting on a cert the operator cannot renew in scope, or noise? *Blocks:* CONN-14's key set and CONN-15's exemption list.
4. **Does the inbound HTTP listener (ADR 0023) need application-layer authentication (bearer / HMAC signature) before any partner-facing deployment, or are mTLS + `source_ip_allowlist` + the bind guard the accepted control set to document and test as such?** There are zero auth references in `http_listener.py` and ADR 0023 defers it. *Blocks:* CONN-30's assertions and CONN-42's on-box row.
5. **Which connectors belong in the on-box WIN2025 §D section?** Email, Direct S/MIME, DICOMweb, the inbound HTTP listener and PassThrough have no row, and three of the five are PHI paths. *Blocks:* CONN-39 through CONN-43 and exit criterion 9.
6. **Is a containerized live SFTP/FTPS CI leg acceptable, and should `[sftp]` be installed in the main `test` leg** so paramiko-backed code is imported at all (it is in no leg today)? *Blocks:* CONN-23 and CONN-24.
7. **Should MLLP `no_ack` (ADR 0124) be permitted on a PHI-bearing outbound, given it finalizes on a TCP write with no partner confirmation — and if yes, what operator-visible marker must the disposition carry?** *Blocks:* CONN-22's pass criteria and any wiring-policy refusal.
8. **Should SFTP key support extend beyond RSA (`remotefile.py:411`) to Ed25519/ECDSA, or is RSA-only a documented constraint we pin with a test?** Modern partners default to Ed25519. *Blocks:* CONN-25.
9. **Who owns keeping `docs/FEATURE-MAP.md` §1 and the `docs/CONNECTIONS.md` connection-type table true, and may we bind both to the connector registry with a drift test** — the mechanism `tests/test_communications_inventory.py` already uses for the ASVS and resource tables? *Blocks:* CONN-36 and exit criterion 12 here; the FEATURE-MAP half is executed as **MIG-74** (CONN-32/CONN-33 point there), so the answer must reach the MIG chapter too.
10. **Is a real partner lab (PACS, HISP, SMART FHIR sandbox, SOAP partner, X12 partner, SMTP relay) in budget for release certification, or do we certify against simulators and record the residual?** *Blocks:* CONN-44, CONN-46, CONN-59 through CONN-63, and how exit criterion 13 counts `external` rows.
11. **Confirm ADR 0020's raw-frame `protocol_trace` tier is permanently declined** so this plan records it as declined-by-design (matching the ADR's own status) rather than an open gap. *Blocks:* CONN-38 and whether any future proposal to capture raw frames at rest needs a fresh ADR.
12. **Should the listener `SSLContext` be rebuilt on config reload (or on file mtime change) rather than only at construction** (`mllp.py:1324`, `http_listener.py:292`, `dicom.py:178`)? Today an in-place cert rotation silently does nothing until a restart, and the only prior signal is an expiry alert the operator may have silenced after "rotating". *Blocks:* CONN-16 and CONN-64's expected result.
