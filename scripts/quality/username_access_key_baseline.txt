# ---- BOUNDED: the username selects the rows, the account's lifetime limits them --------------------

# `GET /me/security-events` -> AuthService.security_events_for(identity.username) ->
# store.security_events_for_user(username), whose SQL is (store._security_events_where):
#     ... WHERE actor = ? AND action LIKE 'auth.%'
#         AND ts >= (SELECT created_at FROM users WHERE username = ?)
#
# The username still decides which rows the caller sees, so the key stays here: `audit_log` has no
# immutable actor id to re-key onto, and adding one means a schema change to a table carrying a
# `row_hash` tamper-evidence chain. The lower bound was the cheaper fix (finding D-2 of the
# 2026-10-02 full review, BACKLOG #1152): the feed starts at the CURRENT account's `created_at`, so
# a deleted account's history under the same name, and a failed sign-in recorded under a name
# before any account held it, both fall outside it. With no account by that name the subquery is
# NULL and no row matches. tests/test_api_auth.py drives both cases through the route.
# Not covered: a directory rename onto the name, or a provision-admin repair of an existing
# row, keeps `created_at`, so rows under the name from before stay inside the bound
# (store._security_events_where says so).
auth_routes.py::security_events_for::arg0
