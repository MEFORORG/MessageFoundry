# Filing request: SQL Server store cancel path segfaults the process

From Manager busy-elgamal-b1c6a6 (acct-1), batch 137. Found by the ADR 0157 Inc 3 measurement for BACKLOG #1497. Please allocate a vault number and file it. This file is untracked and will be deleted once filed.

**Proposed heading:** The SQL Server store's cancel path can segfault the process: `_cursor` and `_release_dirty` close ODBC handles while the abandoned statement still runs

**Cluster:** HA correctness / store. **Priority:** P1 (proposed). **Verdict:** build.

**Severity:** conditional (CLAUDE.md section 0). Zero deployments. A deploying site on SQL Server would hit it when a store call is cancelled mid-statement: engine shutdown, a demotion stop, or any task cancellation that lands during a blocking statement. The whole engine process dies, not one connection.

## What was measured

Engine branch `b137-1497-inc3-probe` (measurement only, not for merge), `tests/test_adr0157_inc3_cancel_probe_sqlserver.py`, run via `workflow_dispatch` on the hosted `sqlserver-store` job, run 36219288548, jobs 108341393874 (SQL Server 2025) and 108341393938 (2022).

- The `claim_ready` case (claim UPDATE parked behind another session's table lock, coroutine cancelled, blocker then releases) segfaulted in 4 of 4 attempts across both legs, about 1.5s after arming, which is when the blocker releases.
- The crashing thread is the store's executor thread (`mefor-sqlserver`). Native stack: pyodbc, then `libodbc SQLDescribeColW`, then `libmsodbcsql-18.7 SQLDescribeColW+0xc4`, so it dies while describing the finished statement's result columns.
- The house-idiom case (write, then `WAITFOR`, cancel) segfaulted once (2022, attempt 3) when the `WAITFOR` ended, frame inside pyodbc.
- `scripts/ci/retry-native-crash.sh` logs every such crash as the known pyodbc #1459 parameter-binding segfault. **These are not #1459.** They are caused by the cancel. So the wrapper's diagnosis can hide this class on any leg.

## Suspected mechanism (inferred, not verified)

On cancellation, `_cursor`'s `finally` closes the cursor and `_release_dirty` closes the raw connection, each off the event loop on another thread, while the abandoned statement is still executing on its executor thread. When that statement returns, pyodbc describes result columns on handles already freed.

## What is already settled by the same run

A cancelled write in the store's usual transaction pattern, and in `mark_done`, was **rolled back, not committed** (locking read with `READCOMMITTEDLOCK` and `LOCK_TIMEOUT 0` returned the pre-write value on both versions). That answer belongs to #1497 Inc 3, not to this item.

## Related

- `claim_fifo_heads` has a shielded `finally` (around `messagefoundry/store/sqlserver.py:7661-7684`) that runs `SET LOCK_TIMEOUT -1;` then `_commit`, so a cancel there commits whatever its claim statement had done. Read by the probe builder, not measured.
- **Round 2 reproduced it in isolation.** Run 36223227696, head `7094dc4e3`, each case in its own child process. SQL Server 2025 (job 108352322839): `claim_ready_blocked_then_completes.write: CRASHED_NATIVE (rc=-11 ...)`, top frames `libmsodbcsql-18.7.so.1.1 +0xc1b17; +0xc2695; SQLColAttributeW+0x1fc; libodbc.so.2 SQLColAttr...`, at the moment the blocker released. SQL Server 2022 (job 108352322940) did not crash that attempt and read ROLLED_BACK, so it is intermittent, not version-exclusive (round 1 crashed on both versions).
